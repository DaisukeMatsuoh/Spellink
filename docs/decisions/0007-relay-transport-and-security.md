# 0007. プラグイン⇔ブリッジ間の通信方式とセキュリティ

- 状態: Accepted（実機で確認 2026-11-07。平文 hello の削除は残作業）
- 日付: 2026-10-30

## 背景
Wi-Fi 越しのやり取りなので暗号化したい。gRPC や UDP の独自プロトコルも候補に挙がった。

## 決定（案）
- 通信路: **WebSocket**（React Native に標準搭載。双方向・ストリーミング可・ネイティブコード不要）。
- 暗号化: **Noise Protocol**（WireGuard と同じ設計の枠組み）でアプリ層を暗号化する。暗号部品は監査済みの純 JS 実装（@noble/curves, @noble/ciphers 等）を使い、暗号そのものは自作しない。
- ペアリング（初回だけ）: ブリッジが短いコードを表示 → Supernote 側で入力。コードを元に PAKE（パスワード認証付き鍵交換）で互いの公開鍵を交換し、以後はその鍵を固定（ピン留め）。
  公開鍵はブリッジ ID を兼ねる。Anthropic の認証情報はブリッジの外に一切出さない。
- 代替案: TLS（wss://）＋自己署名証明書のピン留め。RN の WebSocket で独自の証明書検証をするにはネイティブモジュールが要るので、
  PluginHost が平文 ws:// を許可しない場合にこちらへ切り替える。

## gRPC / UDP を採らない理由
- RN ではどちらもネイティブモジュールが必要（ARM 開発機では Gradle 周りが重くなる）。
- 遅延のほとんどは Claude の生成時間（数秒）で、通信路の差（ミリ秒）は体感に出ない。
- 電力も主に Wi-Fi の電波を起こすコストで決まり、プロトコルの軽さでは変わらない。
- UDP を自作すると、再送・順序保証・暗号化を自分で作ることになり、バグと脆弱性の温床になる。

## 検証項目
- PluginHost のネットワークセキュリティ設定で、LAN の平文 ws:// / http:// が許可されているか。
- Nomad の CPU で純 JS の鍵交換にかかる時間（初回接続時のみ）。

## 追記（2026-10-31）: スパイク版の状態
- スパイク版は **平文 WebSocket + 共有トークン**（`hello` で提示、ブリッジ側は SHA-256 を定数時間比較）で実装。
  同じ LAN の盗聴者からは質問・回答・トークンが見える状態なので、**Noise による暗号化を入れるまでは自宅など信頼できるネットワーク限定**。
- 実機で平文 ws:// が通るかを診断画面で確認してから、Noise（ws:// の場合）か TLS ピン留め（ネイティブ）かを決める。

## 追記（2026-11-01）: Noise を実装
- 方式: `Noise_NNpsk0_25519_ChaChaPoly_BLAKE2s`。事前共有鍵はペアリングトークンから導出（`SHA-256("spellink-psk-v1:" + token)`）。
  鍵を持っていること自体が認証になり、セッションごとに一時鍵で前方秘匿性も得る。PAKE は使わず、トークンはペアリングファイルで渡す。
- ブリッジ: `internal/securechan`（`github.com/flynn/noise`）。最初のフレームがバイナリなら Noise、テキストなら旧来の平文 hello（**LAN のみ**、中継経由は拒否）。
- プラグイン: `src/noise.ts`（`@noble/curves`・`@noble/ciphers`・`@noble/hashes` の基本関数の上に、仕様どおりの状態機械を最小限で実装）。
  `crypto.getRandomValues` が無い環境では、多数の `Math.random()` と時刻をハッシュした代替乱数を使う（弱いが、事前共有鍵があるので秘匿性と認証は保たれ、前方秘匿性だけが弱まる）。
  Noise が端末上で動かない場合のみ、LAN の URL に限って平文にフォールバックする。診断画面に方式（noise / plaintext）と乱数源を表示。
- 確認: Go 同士のテスト（大きなメッセージの分割、誤った鍵の拒否）、TypeScript 実装と Go ブリッジの相互接続（Node 上で実 Claude Code まで）、改ざん検出、代替乱数。
- 未確認: 端末の JS エンジン（Hermes）上で動くか（BigInt・乱数源）。→ 診断 1 で確認。
- 平文 hello は、端末で Noise が動くと確認できたら削除する（下の 2026-11-07 の追記で確認済み。削除は残作業）。

## 追記（2026-11-01）: 実機の結果 — 平文は禁止、TLS（公的 CA）が必須
- Nomad（Chauvet 3.31.45）の PluginHost は **http:// と ws:// をネットワークセキュリティポリシーで拒否**する
  （`CLEARTEXT communication to 192.168.2.180 not permitted by network security policy`）。同じ端末のブラウザからは届くので、PluginHost 固有の制限。
- `.local`（mDNS）の名前解決もできない。
- 自己署名証明書を信頼させるにはネイティブモジュールが要る（この ARM 機ではビルド不可）ので、**公的 CA の証明書を持つ wss:// が唯一の現実的な経路**。
- 結論: 家の中でも、Cloudflare（トンネル）経由の wss:// でブリッジ／中継に届ける。端末⇔ブリッジ間は Noise で暗号化しているので、Cloudflare に中身は見えない。
- ブリッジは、プロキシ経由（`Cf-Connecting-Ip` / `X-Forwarded-For` ヘッダ付き）の接続には Noise を必須にした。
- 検証: Cloudflare クイックトンネル（一時 URL）経由で、プラグインの接続コードから Noise 接続 → 回答受信を確認。平文は拒否されることも確認。
- LAN の ws:// URL はペアリングファイルに残っていても即座に失敗するだけで害はないが、正式版では外す。

## 追記（2026-11-07）: 実機での確認と状態の整理
- 端末（Nomad）から、Cloudflare の名前付きトンネル（`wss://bridge.spellink.uk/v1`）経由で、Noise の接続が成立し、質問・回答が動いている（トレースの `ask.connected` が `mode: noise`、`url: wss://bridge.spellink.uk/v1`）。端末の JS エンジン（Hermes）上で Noise が動くことも確認できた。
- トンネルの終端は Cloudflare のエッジ。エッジからブリッジまでは、同じ機械の中の平文 http（Service は HTTP）。Cloudflare に見えるのは暗号文だけ。
- 残作業: 平文 hello（LAN のみ）の削除、ペアリング情報の端末側保存の決定（公開版に向けて。`docs/notes/progress/README.md`）。
- 接続の切断への対策は ADR 0013（番号つきフレームでの再開）を参照。
