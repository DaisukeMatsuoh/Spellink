# 0010. 外出先からの接続は Spellink の中継サーバ（ランデブー）で受け持つ

- 状態: Proposed（ホスティング先の決定待ち）
- 日付: 2026-10-31

## 背景
ブリッジは家や職場のルーターの内側（NAT の裏）で動く。外から内側の PC へ直接は接続できないので、
外出先の Supernote からブリッジに届かない。Cloudflare Tunnel などを利用者に用意してもらう案は、一般の利用者には難しすぎる。

## 決定（案）
**ブリッジもプラグインも、外にある中継サーバへ「外向きに」接続し、中継サーバが両者をつなぐ。**
ルーターの設定やポート開放は不要（外向きの接続はほぼどのネットワークでも通る）。ngrok や Tailscale の中継（DERP）と同じ考え方。

```
[家の Mac / PC]                          [中継サーバ relay.spellink…]                 [外出先の Supernote]
spellink-bridge ──常時接続（外向き）──▶  ルーム（ペアリングで決まる ID）  ◀──質問のときだけ接続── plugin
                 ◀──── 暗号化されたまま中身を中継（中継サーバは読めない）────▶
```

- **待ち受け**: ブリッジは起動時に中継サーバへ WebSocket を 1 本張り、自分のルーム ID を登録して待つ（約 45 秒ごとの ping で NAT を維持。PC の負荷・通信量はごくわずか）。
- **接続**: プラグインは、LAN の URL と中継の URL に同時に接続しにいく（既存の並列接続の仕組み）。家では LAN、外では中継が勝つ。
- **セッション**: プラグインが中継に来たら、中継は制御用の接続でブリッジに知らせ、ブリッジがそのセッション用の接続をもう 1 本張る。中継はその 2 本のフレームをそのまま流すだけ。
- **端末⇔ブリッジ間の暗号化（必須）**: 中継経由では ADR 0007 の Noise を必須にする。中継サーバが見えるのはルーム ID・通信量・時刻だけで、質問・回答・トークンは見えない。
- **ペアリング**: ブリッジが短いコードを表示 → 利用者が Supernote に入力 → コードから鍵交換（PAKE）して、鍵とルーム ID を両側に保存。
  これ以降、利用者が中継を意識することはない。
- **実装**: 中継も Go で書き、同じリポジトリに置く（`spellink-bridge relay` サブコマンド、または `relay/`）。公式インスタンスを用意しつつ、自分で立てたい人は同じバイナリで自前運用できる。

## ホスティングの候補（決めること）
| 候補 | 長所 | 短所 |
|---|---|---|
| 小さな VPS / Fly.io などで Go の中継を動かす | ブリッジと同じ言語・コード。自前運用の手順もそのまま。移転が容易 | サーバの面倒（更新・監視）を見る必要がある |
| Cloudflare Workers + Durable Objects | 世界中の拠点、運用がほぼ不要、WebSocket の休止機能で待機コストが小さい | 中継だけ JS/TS で別実装になる。Cloudflare に依存 |
通信量の目安: 回答 1 回あたり数十〜数百 KB（ストロークのデータ）。ストロークの圧縮（差分符号化）を入れればさらに小さくできる。

## 理由
- 利用者はブリッジを起動してペアリングするだけでよく、ルーター・VPN・トンネルの知識が要らない。
- 中継は暗号化された中身を流すだけなので、Claude の利用を仲介したり、認証情報に触れたりしない（ADR 0005 の前提を崩さない）。
  ただし公開サービスとして始める前に、Anthropic の規約の「利用の仲介」に当たらないかを改めて確認する。
- 公式の中継を、寄付（Buy Me a Coffee など）で運用費をまかなう対象にできる。自前運用もできるので、利用者を縛らない。

## 前提・依存
- ADR 0007（Noise による暗号化）の実装が先に必要。
- プラグイン側で鍵とルーム ID を保存する手段が要る（現状プラグインからテキストファイルを書けない → ネイティブモジュールか別の方法。実機検証の結果しだい）。
- PC がスリープすると、どの方式でもブリッジには届かない（スリープ抑止オプションで対応）。

## 追記（2026-11-01）: 実装とホスティング
- 実装済み: `spellink-bridge relay`（中継）、ブリッジ側の常時接続（設定 `relayUrl`、指数バックオフで再接続、30 秒ごとの ping）、
  `pair` の出力に中継経由の URL（`…/v1/relay/client?room=<トークンのハッシュ>`）を追加。中継はトークンを知らない。
- 中継経由のセッションは Noise 必須（平文の hello は拒否）。テスト: 中継経由の暗号化セッション、平文の拒否、ブリッジ不在時の 4404。
  この機械で実 Claude Code を使った中継経由の質問（ページ送りを含む）も確認済み。
- ホスティング: ユーザーは Go で決定。フェーズ 1 は自宅（この機械）＋ Cloudflare Tunnel を推奨（`docs/notes/research/2026-11-01-relay-hosting.md`）。
