# 0013. 回答は接続から切り離し、番号つきのフレームで再開できるようにする

- 状態: Proposed（実機で `closed (1006)` が出ても最後まで書けるか確認後に Accepted）
- 日付: 2026-11-07

## 背景
実機で、回答の書き込み中に `closed (1006)` が出て、途中で止まることがあった（2026-11-07、ページをまたぐ回答）。
ブリッジのログは「done」まで進んでいたが、端末は `done` を受け取っていなかった。ブリッジは送信の失敗を記録しておらず、切れたのが Cloudflare の経路か、端末側かは分からなかった。
それまでの作りでは、接続が切れると、(1) 端末は失敗として中断し、(2) ブリッジは接続の終了で質問も取り消していた。どちらも、切断が原因でも、回答が失われた。

## 決定
1. **回答は接続から切り離す。** ブリッジは、質問ごとに「run」を持つ。run は WebSocket より長く生きる。明示的な `cancel`、または、接続している端末が誰もいない状態が 90 秒続いたときだけ止まる（Claude の使用量を無駄にしないため）。
2. **回答のフレームに通し番号 `seq` を付けて、ブリッジが保存する。** `line`・`done`・回答を終わらせる `error` が対象（進捗の `status` は保存しない）。完了した run は 10 分間、最大 16 件まで保持する。
3. **端末は、完了前に接続が切れたら、1 回だけ再接続して `resume {id, next}`（受け取った最後の番号の次）を送る。** ブリッジは `next` 以降のフレームを再送し、続きはそのまま送る。再送と新しいフレームの間に、重複や欠けは出ない（同じロックの下で行う）。端末は、`seq` が既に処理した番号以下のフレームを捨てる。
4. 再接続の試みは 1 回の切断につき 1 回で、時間をおいた再試行のループはしない。1 回の回答での再接続は最大 3 回。再接続できない、またはブリッジがその回答を覚えていない（`unknown_ask`。ブリッジの再起動や 10 分経過）ときは、元の切断の理由を表示して止まる。
5. ブリッジは、送信の失敗と、接続が終わった理由をログに残す。
6. 端末のフライトレコーダーに、重い SDK 呼び出し（`saveCurrentNote` / `insertNotePage` / `jumpToPage` / `getElements` / `getNotePageTemplate`）の**開始**も記録する（これまでは完了時だけで、返ってこない呼び出しが見えなかった）。

## 理由
- 切断の原因（トンネル、端末の処理待ち、ホストの一時停止）が何であっても効く。原因の推測に頼らない。
- 識別は、質問の ID と通し番号だけで行う。推測や回数で帳尻を合わせない（ユーザー方針）。

## 結果・注意
- **これは切断への対策で、切断の原因の解明ではない。** 失敗はページをまたぐ直前だった。端末のページ追加（保存 → ページ挿入 → 移動）の最中にホストが止まる可能性は、まだ検証できていない。記録（6）で、次に起きたとき、どの呼び出しの途中だったかを読む。
- 端末側の書き込みは、これまでも 1 本の列（Promise の連鎖）で順番に待っている。ページ挿入と移動を待ってから、そのページ番号を指定して書く。並列には進まない。
- ブリッジの run は、メモリ上だけにある。ブリッジを再起動すると再開できない。
- 接続が切れても質問を取り消さないので、端末が戻らなければ、最大 90 秒分の Claude の使用量が余計にかかりうる。
