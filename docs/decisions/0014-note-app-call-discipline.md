# 0014. ノートアプリへの依頼は 1 本ずつ・結果まで確かめて進める

- 状態: Proposed（実機で、ページをまたぐ回答とページ追加が最後まで動くか確認後に Accepted）
- 日付: 2026-11-07

## 背景
ページをまたぐ回答で、`closed (1006)` による中断や、ページが空に見える現象が起きていた（ADR 0013）。点検の結果、プラグインの SDK 呼び出しに次の穴があった。

- SDK は `success`（呼び出しが通った）と `result`（実際にできたか）を分けて返す。ドキュメントは、`saveCurrentNote` は「`result: false` = 保存失敗」、`insertNotePage` は「`false` = 挿入失敗」と定めている。私は `success` しか見ず、`result` を捨てていた。保存が拒否されても次のページ挿入に進み、保存前の編集が失われる可能性があった（挿入はキャッシュをファイルから読み直す）。
- ページ挿入の成否を、ページ数で確かめていなかった。
- タイムアウトは「待つのをやめる」だけで、ホストはその呼び出しを実行し続けているかもしれない。次の依頼や中断の処理が、それと重なりえた。
- 要素の読み取り（最大 16 本を同時）と待機中のアニメーションの書き込みが、ホストに同時に依頼を出していた。
- 失敗の握りつぶし: 無応答を「ノートが閉じられた」「ペン情報なし」「一括書き込み非対応」と取り違える、ページ読み取りの失敗を黙って無視する、アニメーションの後始末の失敗を記録しない、`setLassoBoxState` は SDK 呼び出しの共通処理を通らず時間切れもない。

## 決定
1. **ノートアプリへの依頼はすべて 1 つの列を通し、同時に 1 本だけ送る**（`sdk.ts` の `native`）。次の依頼は、前の依頼が**終わってから**送る。タイムアウトで見切った依頼も、ホストが終わらせるまで列は進めない。列での待ち時間もタイムアウトに含めるので、ホストが止まっている間、新しい依頼は積み上がらず、すぐ `CallTimeoutError` になる。待っている間に呼び出し側が諦めた依頼は、あとから送られない。
2. **`result: false` は失敗として止める**（`callChecked`）。保存、ページ挿入、要素の挿入、要素の削除が対象。`jumpToPage` の拒否は、書き込み（ページ番号を指定する）に必要ないので、記録するだけで続ける。
3. **ページ挿入は、挿入の前後でページ数（`getNoteTotalPageNum`）を読み、増えたことを確かめてから書く。** 増えなければ止める。保存が拒否されたら、挿入に進まない。
4. **要素の読み取り（点列）も、同じ列を通し、1 本ずつ読む。** 以前の最大 16 並列はやめた。時間切れまでに読める本数が減るので、混んだページでは空き領域の判定が粗くなりうる（`scan` の記録で、読んだ本数を見られる）。
5. **無応答を別の失敗と取り違えない。** `ensureOpen`、ペン情報、一括書き込みの判定、ページ読み取り・走査は、`CallTimeoutError` をそのまま上げる。それ以外の読み取りの失敗は、記録して続ける（空き領域なしで書く）。
6. **記録を足す。** ブール値の `result` を記録（実機が実際に何を返すかを知るため）、`getElements` の null、走査の本数、アニメーションの失敗（`wave.giveUp`）、`*.refused`、`insertNotePage.notGrown`。

## 理由
- 「1 つずつ完了を確かめてから次を依頼する」を、各呼び出し側の心がけではなく、仕組みで保証する。
- ホストが止まったときに、依頼が重なってさらに悪化することを防ぐ。
- 保存が拒否されたまま進む、挿入が空振りしたのに書く、という「確認せずに進む」経路をなくす。

## 結果・注意
- `getNoteTotalPageNum` の戻りが数値でなければ、ページ追加は失敗として止まる。実機の戻り値が仕様と違うと、複数ページの回答が止まるので、最初の実機確認で見る。
- 追加の依頼（ページ数の取得 2 回）で、ページ追加が少し増える。
- 列は、1 つのプラグインプロセスの中だけ。ホスト側の別の処理（ユーザーの操作）とは調整できない。
- この対策は、ホストが止まる原因を取り除くものではない。重なりと確認不足を取り除いたうえで、止まる状況が残るか、記録（`*.begin`）で調べる。
