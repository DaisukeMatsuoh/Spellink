# 0016. ペアリング: ブリッジが端末ごとの秘密を発行し、台帳で管理する

- 状態: Proposed（実装済み 2026-11-20。表 `docs/spec/pairing.md` は確認済み。実機でのペアリング全体の確認待ち）
- 日付: 2026-11-20
- 経緯: `docs/notes/research/2026-11-08-pairing.md`、実機の結果は `docs/notes/progress/log/2026-11.md`（2026-11-19/20）

## 背景
- 認証と会話ログを持つのはブリッジなので、**どの端末が話してよいかはブリッジが決める**のが筋。
- 端末には、カメラも入力もクリップボードも保存の API もない。公開版のプラグインに、利用者のブリッジの接続情報は入らない。
- 実機で分かったこと:
  - 書き換えた `.snplg`（`Spellink.bundle` は JS のテキスト）はそのまま入り、動く。削除せずに入れ直すと置き換わる（プラグインは初期化される）。
  - 端末の ID を返す API はない。
  - `file://` は `/proc` と `MyStyle` の実在ファイルを読める。`MyStyle` の `listFiles`・`makeDir` は動く。`deleteDir` を含む手順で、プラグインがハングした。
  - 端末の QR（640px）は、PC のカメラで一瞬で読めた。
  - `http://`・`ws://` は PluginHost が拒否する（ADR 0007）。接続先は、公的 CA の `wss://`（中継かトンネル）。

## 決定
1. **端末ごとに、ブリッジが秘密を作って発行する。** 利用者に秘密を作らせない。
2. **秘密は 2 段にする。**
   - **B（初期の秘密）**: ブリッジが端末ごとに作り、その端末専用の `.snplg` の中に入れる（バンドルの先頭に 1 行足す）。**ペアリングにだけ使え、期限がある（既定 24 時間）。**
   - **K（本番の秘密）**: ペアリングの成立時に、ブリッジが作り、暗号化された通信路（B から作る Noise）で端末に渡す。端末が保存し、以後の通信はすべて K で行う。**B は、K が確かに渡った時点で破棄する。**
   - 意味: インストール用の `.snplg` が USB・クラウドの同期で漏れても、ペアリングの後は無効。端末を失くしたら、ブリッジがその端末の記録を失効させる（他の端末は無関係）。
3. **ペアリングの手順（利用者の操作は 3 つ）。**
   1. ブリッジで「端末を追加」（CLI は `spellink-bridge device add <名前>`、メニューアプリでも同じ）。端末専用の `.snplg` が出る。
   2. 端末にその `.snplg` を入れる（USB・クラウド・ファイル共有）。
   3. 端末で「ペアリング」を押す。**ペアリングモード（既定 90 秒。`windowSec`、10〜600 で可変）**に入り、画面に **QR と 8 桁の数字**を出す。ブリッジ側で、QR をカメラで読む（ブリッジが `127.0.0.1` で出すページの JS）か、数字を打つ。一致したら、K が渡る。
4. **画面に出す数字（コード）は、秘密ではない「選択子」。** 端末が乱数で作り、B で暗号化した通信路でブリッジに送る。ブリッジは、利用者が入力したコードと一致する**待ち中の要求 1 つ**にだけ K を渡す。B や K は画面にも QR にも出さない。
   - 盗み見・総当たりの対策: 同じコードの要求が 2 つ来たら**両方を取り消す**（コードが漏れても、横取りされず、失敗するだけ）。待ち中の要求は 1 つの記録につき最大 4。入力の誤りが 5 回続いたら、その窓を閉じる（窓の ID 単位）。
   - PAKE は使わない: コードは通信路の鍵を作らないので、盗聴されても何も得られない（B が通信路を守る）。
5. **台帳**（ブリッジの `devices.json`、権限 0600）に、記録ごとに `id`・名前・世代 `gen`・状態・B・K・発行時刻・最終接続を持つ。**受け取る側がすべて検証する**（形・長さ・個数）。壊れた記録は読み込まず、記録する（失敗側に倒す）。台帳は 16 件まで。
6. **接続先の経路は、公式の中継（ADR 0010）を既定とする。** 自前のトンネルも設定で選べる（`.snplg` に入れる URL の一覧が違うだけ）。LAN 直結（ADR 0011）は任意の近道。中継の部屋 ID は記録ごとに別（B 用と K 用）。ブリッジは、発行中・使用中の記録の部屋だけを登録する。
7. **QR は、ブリッジ側のカメラが使えるときの近道で、8 桁の入力が主経路。** ブリッジの本体は CLI のまま。デスクトップの常駐アプリ（メニューバー）は、同じ API の上の薄い殻として後から足す（任意）。
8. **端末側の K は、`MyStyle` の下のディレクトリの名前に保存する**（実機で、**端末の再起動をまたいで残り、読み戻しで完全一致**を確認 2026-11-20）。
   - 名前は `k-<id>-<gen>-<K を base64url にした 43 字>`。接続先の一覧も、同じ形で `e-<id>-<gen>-<接続先>` に保存する（`pairGrant` でブリッジが渡す）。`makeDir` で作り、`listFiles` で読む。**削除はしない**（`deleteDir` を含む手順でプラグインがハングした。原因は未特定。削除しない版は問題なく動く）。
   - K を作り直す（再発行）と、`gen` が違う新しい名前が増える。プラグインは、パッケージの `gen` と一致する名前だけを使う。古い名前は残るが、ブリッジが破棄した K なので無害。
   - 見えること: 端末のファイル管理や USB の一覧に K が見える。端末を手にした人は読める。これは、端末の紛失を失効で扱う前提（端末にロックがあれば、それが一次の守り）。
   - 保存先の候補だった「B を長期の秘密として使い続ける」代替は、いまは要らない（表の「代替」は、保存先が使えなくなったときの保険として残す）。

## 比べた案
| 案 | 採らない理由 |
|---|---|
| 8 桁だけで認証（PAKE 含む） | コードは 27 ビット。オフライン総当たりの対策が要る。B で守る方が単純で、強い。 |
| 1 つのブリッジに 1 つの共有トークン（現状） | 端末ごとの失効ができない。`.snplg` の漏れが、そのまま全端末の漏れ。 |
| 端末のシリアルとシードのハッシュ | シリアルを取る API がない（実機で確認）。B と K の 2 段で、端末に固有の ID を要らなくした。 |
| ファイルに K を保存 | テキストを書く API が公開されていない。代わりに、ディレクトリ名に保存する（採用。8）。 |
| 手書きでコードを入力 | 認識の誤りが、ペアリングの失敗になる。端末が表示し、PC が入力する向きの方が確実。 |

## プラグインの更新（すでにペアリング済みの端末に、新しい版を入れるとき）
- **新しいパッケージに、秘密を入れる必要はない。** K は、パッケージではなく、端末の保存（上の 8）にあり、パッケージを入れ替えても残る（実機で確認）。接続先も保存してあるので、**接続設定のない公開用の `.snplg` をそのまま入れて動く**（`pairing.md` の `initial` の 2）。
- ブリッジは何もしなくてよい。更新は、ブリッジから見えない（通常の K の接続が続く）。B は、ペアリング成立のときに破棄済みなので、古い `.snplg` の B は使えない。
- ブリッジの `device package <名前>`（REPACK）は、状態を変えずに `.snplg` を作り直す。ペアリング前（I・Q・G）は B 入り、ペアリング後（A）は接続設定だけ。再発行（REISSUE）は、秘密を変える（古い端末は、ペアリングし直し）。

## 帰結
- ブリッジに「端末の台帳」「端末ごとの `.snplg` の生成（zip の書き換え）」「ペアリングの確認（CLI／カメラのページ）」「複数の PSK を扱う接続（`id` で記録を引く）」が増える。接続の URL は `…/v1?d=<id>`（`id` は公開してよい識別子）。
- プロトコルに `pairRequest` / `pairGrant` / `pairAck` / `pairDenied` が増える（古いブリッジでは `bad_request` で失敗する形にする。ADR 0013 の教訓）。
- Noise の事前共有鍵は、これまでの `SHA-256("spellink-psk-v1:" + token)` を B・K に使う（実装済み）。
- 公開用の `.snplg`（接続情報なし）は、端末で「ブリッジで端末を追加し、専用の `.snplg` を入れてください」と案内する。
- 端末にインストーラ（`.snplg`）が `MyStyle` に何個も残る（実機で 13 個）。B は期限と破棄で無害にするが、端末がペアリング成立後に自分用のインストーラを削除できるか（`deleteFile`）は、未確認。

## 追記（2026-11-26）: 接続先を断片に切って保存する
- **きっかけ**: 運営の中継が 2 つ（日本・米国）になり、トンネルと合わせた接続先（約 340 バイト）が、ディレクトリ名の上限 255 バイトを超えて、実機で「鍵を保存できませんでした」になった。仕様の「255 バイトに収まる分だけ」は、収まらないときの扱いが決まっていなかった。
- **255 の出どころ**: Android のファイルシステムの、名前（1 要素）の上限。512 や 1024 にはできない。
- **決定**: 接続先を、200 文字ずつの断片に切り、`e-<id>-<gen>-<i>-<n>-<断片>` として、断片ごとに 1 つのディレクトリにする（最大 32 断片）。接続先の件数の上限は 4 から 8（接続設定の上限）に。接続設定の検証を通るものは、必ず保存できる。**中継が増えても、形式は変わらない。**
- 退けた案: 中継の URL のホスト名だけを保存し、部屋の ID を端末で計算する案（部屋の元の秘密と K が同じかの確認が要り、形式が中継の作りに依存する）。
- 影響: 古い形（1 本）は読まない。ペアリングし直す。
