# 0017. 家の中の直結: 名前サービスが DNS を持ち、各ブリッジが自分の証明書を取る

- 状態: Accepted（ユーザーが方針を決定 2026-11-21）。実装済み。**実環境（本物の Let's Encrypt・ドメイン・VPS）での確認は未**。
- 日付: 2026-11-21
- 前提: ADR 0011（利用者が自分の Cloudflare トークンで取る方式。これに置き換わる）、ADR 0019（運営の入口）、`docs/spec/lan-cert.md`（状態遷移表）、`docs/guides/architecture.md` §10（図）
- 調査: `docs/notes/research/2026-11-20-direct-connection-options.md`、`2026-11-21-relay-tls-in-scratch.md`

## 何を解決するか
端末のプラグインは、公的な CA の証明書つきの `wss://` にしか接続しない（ADR 0007）。家の中で、中継を通さずにブリッジへ直接つなぐには、**ブリッジの LAN の IP を指す名前**と、**その名前の公的な証明書**が要る。利用者に Cloudflare のトークンやドメインを用意させない。

中継（ADR 0010）の代わりではない。外出先では、ブリッジは家のルーターの内側にいて、外から入れないので、中継が要る。名前サービスは、**家の中の近道**だけを担う。近道が取れなくても、中継で使える。

## 決定
1. **名前は `<id>.lan.spellink.uk`。** `id` は、ブリッジが初回に作る Ed25519 の公開鍵の SHA-256 の先頭 16 バイト（16 進 32 桁）。公開鍵から決まるので、アカウントも審査も要らず、他人は同じ ID を名乗れない。
2. **DNS は名前サービス自身が持つ。** `spellink.uk` のゾーン（Cloudflare）に `lan` の NS レコードを足し、`lan.spellink.uk` 以下を VPS の名前サービスに委任する。名前サービスが権威 DNS（UDP/TCP 53）として、`<id>.lan.spellink.uk` の A レコード（ブリッジの LAN の IP）と、証明書の確認用の TXT を返す。**Cloudflare の API トークンは使わない。**
3. **登録**（`POST /v1/register`）: ブリッジが `{id, publicKey, ip, time, nonce, signature}` を署名つきで送る。名前サービスは、ID が公開鍵のハッシュと一致するか、署名、時刻（±5 分）、nonce の再使用、**IP がプライベートの IPv4 であること**を確かめる。ブリッジは起動のたびと、IP が変わったときに登録する。
4. **証明書は、各ブリッジが自分で、Let's Encrypt から取る**（ACME の DNS-01）。**秘密鍵はブリッジの外に出ない**（CA に渡るのは CSR だけ、名前サービスに渡るのは 43 文字の確認値だけ）。確認値の TXT は `POST /v1/acme`（署名つき）で名前サービスに置いてもらい、注文が終われば消す。名前サービスの側でも 10 分で消える。
5. **利用者ごとに別の名前・別の証明書にする。** 全員に 1 枚のワイルドカードを配る案は採らない（1 人から鍵が漏れると全員が騙られ、失効で全員が止まる。認証局の規約も、鍵を他人に配ることを許さない）。
6. **取れなくても使える。** 直結は近道なので、登録・取得の失敗や待ちは、利用者にはエラーにしない（状態は「準備中」）。再試行の間隔は、CA が示した時刻、なければ固定の表（1 分・5 分・30 分・2 時間・以後 6 時間）に従う。回数の帳尻合わせはしない。
7. **状態は 2 つの機械（登録、証明書）にして、表を先に書いた**（`docs/spec/lan-cert.md`。生成物 `bridge/src/lan/{reg,cert}_table.rs`）。IP が変わっても、証明書は取り直さない（A レコードだけの話）。
8. **既定は無効。** `config.json` の `lan.enabled` を true にしたブリッジだけが使う。名前サービスが本番で動くまで、全員に登録を試みさせないため。動いたら既定を有効にする（1 行の変更）。
9. **古い設定（`lan.host`・`lan.cloudflareToken`、ADR 0011）は使わない。** 読めるが、ファイルは壊さず、使わないとログに出す。

## 名前サービスの守り（`docs/spec/interfaces.md` I28〜I31）
- 書けるのは、`<id>.lan.spellink.uk` の A と、`_acme-challenge.<id>.lan.spellink.uk` の TXT だけ。ID が 32 桁の 16 進でなければ、名前ごと存在しない。
- 接続元ごとの回数制限（API は 60 回/分、DNS は 100 回/秒）、ID の数の上限（10 万）、ID あたりの更新の間隔、本文の上限（4 KiB）、nonce の記憶。
- DNS: 質問は 1 つ、圧縮ポインタなし、ゾーンの外は REFUSED（再帰しない）、ANY は何も返さない、ゾーン転送は拒否、応答は質問より大きくなりにくい（増幅しない）。
- 記録は `names.json`（0600、一時ファイル→名前変更、読み戻し）。180 日更新のない ID は忘れる。

## Let's Encrypt の上限（確認済みの前提）
- 新規 50 枚/週/登録ドメイン。**新しく直結を使い始める人が週 50 人まで**で、利用者の総数の上限ではない。更新は同じ名前なら数えない。
- 上限に達しても、直結が遅れるだけで、中継は使える（決定 6）。
- 足りなくなったら、（a）登録ドメインを増やす、（b）Let's Encrypt の例外申請、（c）予備の CA（Google Trust Services。運営の Google Cloud アカウントの EAB が要るので、名前サービスが利用者ごとに EAB を発行する仕組みが要る）。最初は Let's Encrypt だけ。

## 比べた案
| 案 | 採らない理由 |
|---|---|
| 利用者が自分の Cloudflare トークンで取る（ADR 0011） | 利用者に、ドメインとトークンを用意させる。一般の利用者には難しい |
| 運営の Cloudflare に名前サービスが DNS を書く | 運営の DNS 用トークンが、VPS に置かれる（漏れると全ゾーンが危ない）。レコード数の上限もある |
| 全員で 1 枚のワイルドカード | 決定 5 |
| 自前の CA を立てる | 端末は公的な CA しか信頼しない |

## 結果・注意
- 名前サービスには、ブリッジの ID と LAN の IP が見える（内容・鍵は見えない）。プライバシーの文書に書く。
- ルーターの DNS リバインディング対策（公開の名前がプライベート IP を返すのを遮断）がある家では、直結が失敗し、中継が使われる。利用者向けの文書に例外設定を書く。
- VPS は UDP/TCP 53 を開ける（運営側の守りは ADR 0019）。

## 追記（2026-11-22）: 週 50 枚の枠の扱い（ユーザーが決定: 45 と 5）

**前提の訂正:** 上の（a）「登録ドメインを増やす」は、`lan1.`、`lan2.` のようなサブドメインを増やすことではない。Let's Encrypt は、**公開サフィックス一覧（PSL）で決まる「登録ドメイン」**で数える。`lan1.spellink.uk` も `lan2.spellink.uk` も `spellink.uk` に数えられ、サブドメインを分けても枠は分かれない。

**直結は、普通の利用者の経路である**（家の Wi-Fi で、PC と端末が同じ LAN にいる場合）。公開するときは既定で入れる。そのため、枠は「週に増える新しい利用者の数」にほぼ等しい。

**決定: ドメインは 1 つ（`spellink.uk`）のままにする。** 利用者に「怪しい別ドメイン」を見せない。費用も増やさない。代わりに、次の 4 つで備える。

1. **枠の予約。** 名前サービスは、1 週間（直近 7 日）に直結のために発行を始める証明書を、**45 枚まで**に絞る。残り 5 枚は、中継・名前サービス自身の**新規**発行（新しい地域の中継を足すなど）のために空けておく。更新は枠を使わないので、既存の中継の証明書は、枠が尽きても更新できる。
2. **尽きたときの見え方。** 上限に達した間の登録には、「今週の直結の枠が埋まっています。中継で動いています。次の枠が空いたら、自動で直結に切り替わります」と返す（ブリッジの状態に出す）。順番は、先に来た順。利用者の端末は、中継で動き続ける（決定 6）。
3. **広まる前に出す申請。** Let's Encrypt の枠の引き上げ（override）の申請を出す。無料で多数の利用者に名前を渡す運営は、通ることがある。
4. **後から効く手。** `lan.spellink.uk` を PSL の PRIVATE セクションに載せる。載れば、`<id>.lan.spellink.uk` が 1 つずつ別の登録ドメインとして数えられ、枠が実質なくなる（DuckDNS などと同じ仕組み）。ただし、PSL の管理者は、小さな・実験的な・短期のものを断る。一定の利用者がいる実績ができてから申請する。審査と反映には数週間〜数か月かかる。さらに、予備の CA（Google Trust Services。上の（c））は、それでも足りないときに考える。

**やらないこと:** 枠のためだけの別ドメイン。ID でゾーンを分ける複数ドメイン。

**数え方（実装）:** 名前サービスが、ID ごとに「初めて注文を始めた時刻」を持ち、直近 7 日に 45 を超える ID が始めないように、新しい ID の最初の TXT の設定を断る（`429 lan_quota`、空く時刻つき）。更新と、同じ ID の再試行は数えない。運営の中継・名前サービスの ID は、`--infra-ids` で指定すると、数えず、断らない（5 枚の予約）。ブリッジは、断られたら、その時刻まで中継で動き、空いたら自動で直結を取り直す（状態表の `RateLimited` と同じ扱い）。詳細は `docs/spec/lan-cert.md` の L9。

**確認が要る点（実環境）:** Let's Encrypt の枠の数え方は、公式の説明（<https://letsencrypt.org/docs/rate-limits/>）に従う。45 と 5 の配分は、実際の利用が分かってから見直す。名前サービスの数え方は、失敗した注文も数えるので、Let's Encrypt の実際の消費より多めになる（安全側）。
