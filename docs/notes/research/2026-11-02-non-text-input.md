# 文字以外の手書き（楽譜・図・数式）を扱う構想（2026-11-02）

きっかけ: 音符を書いてラッソで囲んだところ、文字認識が `null` を返し、エラーになった（修正済み: 小さなダイアログで「文字として読み取れない内容です」）。
ユーザーの問い: 認識できないとき、ストロークのデータそのものを送れないか。将来は楽譜のような実用的な表記に対応できないか。

## プラグインが取れるデータ（SDK で確認済み）
| データ | API | 中身 |
|---|---|---|
| ストロークの点列 | `getLassoElements()` → `Element.stroke.points` | 座標 (x, y)。ページ実寸の px |
| 筆圧 | `stroke.pressures` | 0〜4096 |
| 時間順の点 | `stroke.recognPoints` | X, Y, Flag, timestamp（書いた順・速度が分かる） |
| ペン情報 | `stroke.penType / penColor`, `thickness` | 種類・色・太さ |
| 範囲 | `getLassoRect()` | 選択矩形 |
| 画像 | `generateLassoPreview(path)` | 選択範囲の PNG |
| 文字 | `recognizeElements()` | 端末内の文字認識。図・楽譜では `null` |

つまり、**ストロークそのもの（ベクトル・順序・筆圧）はプラグインから取れる**。ピクセルではなく、書いた過程の記録なので、画像より情報が多い。

> **方針（ユーザー, 2026-11-02）**: 画像を送る方式は、知財調査で気になる点があったため避け、**ストロークデータから画像を作る、または直接意味を取る**方向にする。
> 下の 1（画像を Claude に見せる）は、この方針では優先度を下げる。2（ストロークの要約）と 3（専用の認識器）を中心に検討する。知財の詳細はローカルの `docs/notes/ip/private/`（git 管理外）。

## できること（段階的に）
1. **画像を Claude に見せる**（最短）: 認識が空なら、選択範囲の PNG をブリッジへ送り、Claude の画像入力で読ませる。
   `claude -p` は `--input-format stream-json` で画像を渡せる見込み（要確認）。実装は小さい。精度は Claude の視覚能力しだいで、手書き楽譜の精度は未知。
2. **ストロークの要約を添える**: 点列を間引いた JSON（各ストロークの bbox・向き・長さ・閉じているか）を一緒に送る。
   五線＝長い水平線の群、音符の頭＝小さく閉じた塊、符幹＝短い垂線、のような**幾何の事実**を渡せば、画像だけより読み取りやすくなる可能性がある。
3. **専用の認識器を挟む**: 楽譜なら、ストロークを記号（音符・休符・記号・五線）に分類し、**MusicXML や ABC など意味のあるデータ**にしてから Claude に渡す。
   認識器はブリッジに組み込まず、別プロセス（MCP サーバなど）にして、種別に応じてブリッジが振り分ける。ユーザーが別プロジェクトで進めている楽譜処理を、ここにつなげられる。
4. **書き戻し**: 回答が楽譜・図なら、テキストではなくストロークで描き返す（今のグリフ方式の延長。音符や五線の「グリフ」を作る）。

## 設計上の方向
- ブリッジのプロトコルに「入力の種類」を足す: `text`（今）／`image`／`strokes`。種類ごとに処理を分ける。
- 端末側の判断は単純にする: 文字認識が空 → 画像＋要約を送る（設定でオン/オフ）。通知は小さなダイアログのまま。
- 手書きの内容を外に送るので、**何を送るかを設定画面で明示**する（画像・ストローク）。LAN／トンネル経由でも暗号化（Noise）は変わらない。
