# ペアリング: 端末に「どのブリッジに、どの鍵でつなぐか」を入れる方法

> 状態: **決着** → ADR 0016（端末ごとの 2 段の秘密 B・K、台帳、8 桁のコードの確認）。この文書の A〜D の比較は、そこに至る検討。

2026-11-08。公開版の**最大のブロッカー**（`docs/notes/progress/release-plan.md` の 3.1）について、課題と理由、背景、選択肢、決めてほしいことを 1 か所にまとめた。
すでにある関連の記述: ADR 0010（リレーのペアリング案: 短いコード）、`docs/notes/device-test-guide.md`（`bridges.json` を読む予定）、`docs/guides/bridge-and-relay-for-users.md`（利用者向けの整理）。ここは、それらを**課題として**つなぎ直したもの。

## 1. 「ペアリング」とは、何を渡すことか
端末（プラグイン）が、ブリッジにつなぐために知っていなければならない 3 つ。

| 情報 | 例 | 秘密か |
|---|---|---|
| 名前 | `rock-5b-plus` | いいえ（表示用） |
| **トークン** | 32 文字ほどの文字列（24 バイトの乱数） | **はい。そのブリッジの全権限の鍵**（端末とブリッジの暗号化の鍵もこれから作る） |
| 接続先の URL の一覧 | `wss://bridge.example.com/v1` など（トンネル、リレー、LAN） | いいえ（ただし、知られると、鍵の総当たりの対象になる） |

ブリッジは `spellink-bridge pair` で、この 3 つを JSON にして出す。問題は、**それを端末にどう入れるか**。

## 2. 現状
- **（廃止: 2026-11-22。埋め込みの道は削除した。以下は当時の記録）開発中**: 開発者が、`pair` の出力を `plugin/src/bridges.local.json`（git 管理外）に置き、プラグインを**ビルドし直して**、その中に埋め込んでいる。
- **コードにはあるが、実機で確かめていない道**: 端末の `MyStyle/Spellink/bridges.json` を `fetch('file://…')` で読み、なければ埋め込みにフォールバックする（`plugin/src/bridgeConfig.ts`）。診断画面には、どちらから読んだか（`source`）が出る。実機で、ファイルから読めた記録はない（そのファイルを置いたことがない）。
- **公開用のプラグイン**（`release.yml` の `plugin-v*`）には、ブリッジの接続情報が入っていない。つまり、**今のまま配ると、誰も使えない**。

## 3. 何が課題か、なぜか
1. **利用者ごとにビルドさせられない。** 埋め込み方式は、開発者のための近道。もし、トークンを埋め込んだプラグインを配ったら、それを受け取った全員が**1 つのブリッジの鍵を持つ**ことになる（致命的）。利用者に React Native のビルド環境を要求するのも非現実的。
2. **端末に、保存する手段がない。** SDK には、プラグインが設定を永続的に保存する API がない（そのため、設定はブリッジに保存している）。ファイルを書く API もない。つまり、ペアリングのあとも、**次にプラグインが起動したときに、同じ情報をどこかから読み直せなければならない**。
3. **端末に、入力する手段が乏しい。**
   - カメラ・QR コードの読み取り・クリップボードの API は、SDK に**ない**（`sn-plugin-lib` の中を調べた）。QR は使えない。
   - e-ink の端末で、32 文字のトークンや、長い URL を打つのは、現実的でない。
   - ただし、端末には**手書きの認識がある**（このプロダクトの中核）。短いコードなら、手書きで入れられる。
4. **鍵の扱い。** トークンは、そのブリッジの全権限。置き場所（`MyStyle` のフォルダ）は、USB やクラウドの同期で、ほかへ漏れうる。**端末を紛失したときに、その端末だけを無効にする手段がない**（いまは、ブリッジのトークンを作り直して、全端末を再ペアリングするしかない）。
5. **道によって、渡す量が違う。** 自分の Cloudflare のトンネルなら、利用者のドメインの長い URL が要る。Spellink のリレーなら、短いコードだけで足りる（ブリッジも端末も、リレーに外向きにつなぐので、URL を教える必要がない）。
6. **複数の端末・複数のブリッジ。** 1 つのブリッジに、複数の端末（同じトークンを共有）。1 つの端末に、複数のブリッジ（コードは、複数に対応済み）。

背景として、「この製品は、利用者が自分のパソコンでブリッジを動かす」（ADR 0005）。だから、**他人のブリッジと自分の端末を結ぶ作業が、必ず利用者の手元で発生する**。ここが簡単でないと、技術に詳しくない人は、使えない。

## 4. 選択肢
| 案 | 中身 | 端末への入れ方 | 保存先（問題 2） | 利点 | 欠点・未確認 |
|---|---|---|---|---|---|
| **A. ファイルを置く** | `spellink-bridge pair <ファイル>` で `bridges.json` を作り、端末の `MyStyle/Spellink/` にコピー（USB、Browse & Access、クラウド） | ファイルのコピー | そのファイル（端末の保存領域） | **すぐできる**（コードはある）。リレーが要らない。どの道（トンネル、LAN）でも使える | 手間がかかる。トークンが平文のファイル。複数の端末には、手作業で配る。**`file://` で読めるかが未確認** |
| **B. 手書きの短いコード＋リレー**（ADR 0010 の案） | ブリッジが 6〜8 桁のコードを表示（数分有効・1 回限り）→ 利用者が端末のノートに**手書き** → ラッソ → プラグインが認識 → リレー経由で、コードをパスワードにした鍵交換（PAKE）→ 鍵と接続先が両側に渡る | **手書き** | 別途必要（下の C） | 利用者の手間が最小。トークンが画面にも紙にも出ない。道を意識しない | **リレーの運営が前提**（3.3）。実装が大きい（PAKE、リレー側の会合の仕組み）。保存先が別問題 |
| **B'. 端末が表示 → PC で入力** | 端末の設定画面に、短いコードを**表示** → 利用者がパソコンで `spellink-bridge pair --code 123456` | PC のキーボード | 同上 | e-ink に入力しなくてよい。テレビのペアリングと同じ、よく知られた形 | 同じく、リレー（会合点）が前提。保存先が別問題 |
| **C. ノートに保存する** | ペアリング用のノートを 1 つ作り、そのテキストボックスに情報を書く。プラグインは、そのノートを読んで使う | A / B / B' の「保存先」として | **ノートそのもの**（端末に残る。SDK の `createNote`・`insertText` はあり、診断で `insertText` は成功済み） | 端末の中で完結。保存の API が要らない | ノートの同期・バックアップで、トークンが漏れうる。利用者が消すかもしれない。「どのノートか」を見つける規則が要る。**ノートの文字を読み戻せるか未確認** |
| **D. 端末のキーボードで入力** | RN の `TextInput` で、設定画面に入力 | 画面のキーボード | 同上 | 単純 | **端末でソフトキーボードが使えるか未確認**。長い文字列は、現実的でない（短いコードなら可） |
| ~~E. QR コード~~ | — | カメラ | — | — | **端末にカメラ・QR の API がない。不可** |

整理すると、課題は 2 つに分かれる。**(1) どうやって入れるか**（A のコピー、B の手書き、B' の PC 入力、D のキーボード）と、**(2) 端末のどこに残すか**（A のファイル、C のノート）。

## 5. 実機で確かめること（診断で、まとめて）
1. `MyStyle/Spellink/bridges.json` を置いて、`fetch('file://…')` で**読めるか**（読めれば、A がそのまま使える）。診断画面の `source` と `fileError` に出る。
2. ノートのテキストボックスに書いた文字を、**あとで読み戻せるか**（`getElements` で `textBox` の内容が取れるか）→ C が成り立つか。
3. RN の `TextInput` で、**画面のキーボードが出て、文字が入るか** → D。
4. 手書きで書いた 6〜8 桁の数字の、認識の確実さ（B）。

## 6. 推奨（段階）
- **まず A を、使える形に仕上げる。** リレーの運営が決まっていなくても、他の人が、ビルドなしで使えるようになる。やること: ①実機で `file://` を確認 ②読めなければ、案内を設定画面に出す（「接続先が見つかりません。手順…」）③`pair` の出力を、置き場所つきで案内（`MyStyle/Spellink/bridges.json`）④公開用のプラグインが、接続情報なしで起動したとき、利用者に何をすればよいか伝える。
- **次に、B または B'（コード方式）。** リレーの運営（3.3）を決めてから。保存先は、A のファイルか、C のノート。
- **鍵の扱いを足す**: 端末を紛失したときのために、ブリッジで**トークンの作り直し**（`spellink-bridge token rotate`）。可能なら、端末ごとのトークン（端末別に無効にできる）。
- A の前に、**公開版のプラグインに、埋め込みの接続情報が含まれていないこと**を、CI で確かめる（誤って、開発者の鍵が入った `.snplg` を公開しないため）。

## 7. 決めてほしいこと
1. **最初は A（ファイルを置く）でよいか。** 手間はあるが、すぐ公開版が使える。
2. **リレーを運営するか**（B / B' の前提）。しない場合、利用者は、自分でトンネルを用意し、A で接続する。
3. 端末の紛失への備えは、「ブリッジでトークンを作り直す（全端末を再ペアリング）」で足りるか。端末ごとの鍵は、必要か。
4. 1 つのブリッジに、複数の端末を、同じトークンで共有してよいか。
