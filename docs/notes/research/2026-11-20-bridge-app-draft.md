## 1. 目的と利用者
- 利用者: パソコンに慣れた一般の人。ターミナルを開かない。Claude Code（公式 CLI）を入れてログインするところまでは済ませている人。
- できるようにすること: ①ブリッジが動いているか、Claude Code が使えるかが一目で分かる ②端末を追加し、専用の `.snplg` を保存する ③端末の QR を読んでペアリングする ④端末を失効・再発行する ⑤パソコンを起動したら自動で動く。
- 今の `spellink-bridge` のコマンド（`serve`、`device …`、`service install`）は、そのまま残す（サーバー用途・上級者・CI）。アプリは、同じ機能の**一般向けの入口**。

## 2. 構成（案）
```
[Spellink Bridge App = 1 つのプロセス]
  トレイアイコン（OS ごとの薄い殻）
  └ 同じプロセスの中で ブリッジ本体（今の serve）を動かす
  └ 127.0.0.1 の Web 画面（/app）← 主画面。トレイの「開く」でブラウザが開く
```
- **主画面は Web（ブリッジが 127.0.0.1 で配る HTML）**。今の `/pair` と同じ作り（Syncthing や Plex のやり方）。理由: 3 つの OS で見た目と操作が同じ／文言は TSV のまま多言語／`jsQR` のカメラも同じページで済む／テストが書きやすい（ページの JS は偽ブラウザで試験済み）。ネイティブのウィンドウ部品に依存しない。
- トレイのメニューは**最小**: 状態の行、「Spellink を開く」、「ログイン時に起動」の切り替え、「終了」。
- 1 プロセスなので、自動起動の仕組みは 1 つ（macOS: ログイン項目、Windows: スタートアップ、Linux: XDG autostart）。サービスの `service install` は、画面のない機械向けに残す。
- 管理 API（`/admin/`）と `admin.token`、台帳 `devices.json` は、今のものをそのまま使う。**アプリが新しい鍵の置き場や新しい権限を作ることはない。**

## 3. 画面（`/app`）
1. **状態**（最上部）: ブリッジ ○稼働中／Claude Code ○使えます／×見つかりません（入れ方を案内）／×未ログイン（`claude` でログインする案内）／接続先（中継・トンネル・LAN）の状態。
2. **端末**: 一覧（名前・状態・最後に使った日時）。各行に「失効」「作り直し（再発行）」「セットアップファイルを保存」。
3. **端末を追加**（ウィザード）: ①名前を付ける ②`.snplg` を保存（保存先の選択はブラウザのダウンロード。**0600 は付けられないので、ファイルは短い期限つきで、ペアリング後は無効になる**と説明する）③「端末にコピーして、プラグインを入れる」手順 ④「端末の『ペアリング』を押す」→ カメラが開く（`/pair` と同じ）→ 完了。
4. **設定**: 言語（OS に追従、手動で変更可）、ログイン時に起動、中継の URL（上級者向け。既定は公式の中継）、窓の長さ（上級者向け）。
5. **ログ**: 直近の出来事（個人の内容は出さない。鍵・質問・回答は出さない）。

## 4. 初回の流れ（オンボーディング）
**同意（最初の 1 回）**: 起動の最初に、利用規約の要点（`docs/legal/terms-of-service-draft.md` の 2: このパソコンの Claude Code のログインは自分のもの／自分だけが使う／端末の利用者も自分／Anthropic の規約を守る）への同意を求める。同意した版と時刻を設定に残す（規約が変わったら、もう一度）。同意なしには、端末の追加ができない。
起動 → ①Claude Code の有無とログインを確かめる → ②端末が 0 台なら「端末を追加」を勧める → ③ペアリング完了で「Ask AI をノートで試してみましょう」。途中で閉じても、次に開いたとき続きから。

## 5. 状態（表にする前の洗い出し。`docs/spec/bridge-app.md` に清書する）
- **アプリの状態**: 停止中／起動中／稼働中（正常）／稼働中（Claude Code が使えない: 未導入・未ログイン）／稼働中（端末なし）／異常（ポートが使用中・台帳が読めない・設定が壊れている）。
- **イベント**: 起動、終了、Claude Code の確認の結果、端末の追加・ペアリング完了・失効・再発行、接続先の断・復帰、ポートの競合、設定の変更、OS のスリープ・復帰、**二重起動**。
- **決めておくこと**: 二重起動は 2 つ目を断り、1 つ目の画面を前に出す（ロックはポートと PID）／スリープから戻ったら中継へ再接続／終了のときは実行中の回答を最後まで書くか待つか（待つ上限を決める）。

## 6. 文言と言語
- すべての文言は TSV（`plugin/locales/strings.tsv` と同じ規則。アプリ用の `bridge/internal/app/strings.tsv`）。列は、Supernote の本体の言語（§言語の調査）に合わせ、**en・ja・zh_CN・zh_TW** から始める。
- OS の言語を見て選ぶ。端末の言語とは独立。

## 7. セキュリティの方針
- 画面は 127.0.0.1 だけ。プロキシ・トンネル経由は拒否（`/admin/` と `/pair` と同じ）。管理トークンは URL の `#` の後ろだけで運ぶ（サーバーに送られない）。
- 画面を配る HTTP は、他のサイトから叩かれないように、`Origin`/`Host` を確かめる（DNS rebinding 対策）。**現在の `/pair` と `/admin/` には、まだ Host の検査がない。アプリを作る前に足す。**
- 秘密（鍵・B・管理トークン）は、ログ・画面・エラーに出さない。`.snplg` のダウンロードは認証つき。
- 署名のない実行ファイルは、macOS の Gatekeeper・Windows の SmartScreen が警告する。公開するなら署名が要る（§9）。

## 8. 技術（案）
- **Go**。今のブリッジと同じコードを使う（台帳・サーバー・CLI）。トレイは `fyne.io/systray`（macOS は cgo が要る。Windows・Linux は不要。Linux は DBus の StatusNotifier で、KDE は動く。GNOME は拡張が要る）。
- Rust への移行は、**ブリッジの待機時のメモリ・CPU を測った結果で**決める（先に決めた方針）。アプリの設計（Web 画面＋管理 API）は、言語に依存しない。
- 基になる `Spellink.snplg` は、アプリに**埋め込む**（`go:embed`）。利用者が `pairing.pluginPackage` を設定しなくてよい。更新は、アプリの更新と一緒。
