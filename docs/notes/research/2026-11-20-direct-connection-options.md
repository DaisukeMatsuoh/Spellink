# 中継を通さずに、端末とブリッジを直接つなげられるか（NetBird・WebRTC 型の案の検討）

2026-11-20。ユーザーの問い: 「中継（トンネル）は、常に通信に関わる。最初の宛先の交渉だけに使い、あとはピア・ツー・ピアにできないか。NetBird のように VPN を張れないか」。

## 結論（先に）
- **外出先からは、端末側の制約で、ピア・ツー・ピアにできない。** 中継（フレームを流すだけ）は、今のところ唯一の普遍的な道。ただし、流れるのは回答 1 回あたり数十〜数百 KB で、**費用の主役ではない**（月 1,000 人で 300 GB 程度の見積もり。`2026-11-20-relay-decisions.md`）。
- **家の中なら、「宛先と証明書の交渉だけを中心でやり、通信は直接」にできる。** これは、いまの LAN 直結（ADR 0011）の延長で、**利用者に Cloudflare のトークンを求めない形**にできる。作る価値がある。

## 1. なぜ、外出先でピア・ツー・ピアにできないか
端末のプラグインは、React Native の JS で、使えるのは **`fetch` と `WebSocket`（公的な CA の証明書つきの `wss://`）だけ**（実機で確認: 平文の `ws://`・`http://` は拒否、`.local` は引けない、ネイティブモジュールは足せない）。
| 必要なもの | 端末のプラグインで | 理由 |
|---|---|---|
| WebRTC（ICE・STUN・穴あけ） | **使えない** | ネイティブモジュールが要る（このビルド環境では足せない） |
| UDP・生の TCP | **使えない** | JS から出せるのは WebSocket と fetch だけ |
| VPN（NetBird・Tailscale・WireGuard） | **プラグインからは張れない** | VPN は端末の OS 側の機能。Supernote の OS に、そのアプリを入れられるかは未確認 |
| 外から「待ち受ける」 | **できない** | 端末は、つなぐ側にしかなれない |
つまり、端末が出せるのは、「公的な CA の証明書をもつ、ある名前の `wss://` へ、こちらからつなぐ」ことだけ。ブリッジが家のルーターの内側にある限り、その名前の先に**誰かが待っている**必要があり、それが中継。

## 2. 家の中なら: 「名前と証明書だけ」を中心が配る（Plex の `plex.direct` 型）
LAN 直結（ADR 0011）の課題は、**証明書**（平文は拒否されるので、公的な CA の `wss://` が要る）と、そのための**利用者の Cloudflare トークン**（一般の人には無理）だった。これを、Spellink が運営する小さなサービスで置き換える。
```
[ブリッジ] --(1) 自分の ID と LAN の IP を登録-->  [Spellink の名前・証明書サービス]
[ブリッジ] <-(2) <id>.lan.spellink.uk の A レコードを、その IP で作り、証明書を取る手伝い --
[端末]     --(3) wss://<id>.lan.spellink.uk:8766 へ直接-->  [ブリッジ]   （通信は LAN の中だけ。中心を通らない）
```
- **名前**: `<ブリッジの ID>.lan.spellink.uk` → ブリッジの LAN の IP（プライベートアドレス）。サービスが Cloudflare の API で、A レコードを作る（API トークンは**サービスだけ**が持つ）。
- **証明書**: ブリッジが自分で、Let's Encrypt の DNS-01 で取る。ただし、DNS の TXT レコードは、サービスが代わりに書く（`_acme-challenge.<id>.lan.spellink.uk` を、サービスの管理する名前に CNAME しておく、acme-dns の方式）。**秘密鍵はブリッジの外に出ない**。
- **ID の信用**: ブリッジが、自分の鍵（登録のときに作る）で署名して登録する。他人が、他人の ID の名前を奪えない。
- **Let's Encrypt の上限**: 1 つの登録ドメインあたり週 50 枚。`lan.spellink.uk` を **Public Suffix List** に載せると、各 `<id>.lan.spellink.uk` が別々のドメインとして数えられ、上限の問題が消える（利用者にサブドメインを配るサービスの標準的なやり方。申請は無料で、数週間かかることがある）。
- **効果**: 家では、中継を通らず、速く（ADR 0011 は、トンネルが 0.5〜2 秒かかると述べていた）、中心には「名前の登録」しか見えない。外出先は、従来どおり中継。
- **弱点**: ルーターの「DNS リバインディング対策」が、公開の名前をプライベートの IP に引くことを遮断することがある（例外設定が要る）。そのときは、端末が並列に試している中継が勝つ（失敗しても、使えなくならない）。
- **運営するもの**: Cloudflare の DNS を叩く小さな API（登録・ TXT の代筆）。状態は小さい（ID → 公開鍵・IP・最終更新）。中継と同じ場所で動かせる。

## 3. 外出先で「直接」に近づける、別の道（上級者向けの任意）
- **利用者が自分で、Tailscale など（VPN）を、ブリッジ側と端末側の両方に入れられる場合**: Tailscale の `serve`／MagicDNS は、公的な CA の証明書つきの `https://<機械>.<tailnet>.ts.net` を出せる。Spellink は、その `wss://` を `extraUrls` に書くだけで使える（コードの変更は要らない）。端末の OS に VPN アプリを入れられるかが前提で、**Supernote で入れられるかは未確認**。
- **利用者が自分の Cloudflare Tunnel を用意する**（今の手順書。手間は大きい）。

## 4. 決めてほしいこと
1. **§2 の「名前・証明書サービス」を作るか。** 作るなら、公式の中継と同じ運営の枠に入れる。エージェントは、サービスの設計書（API・認証・登録の流れ）と、ブリッジ側の登録クライアントを作れる。`lan.spellink.uk` の Public Suffix List への申請と、Cloudflare の API トークンは、ユーザー。
2. 外出先は、当面、中継（Cloudflare Tunnel 経由）で行く。
