# 中継（リレー）の運営: 何が分かっていなくて、何を決めるか

2026-11-20。前提: ADR 0010（中継は、暗号化されたフレームを流すだけ）、`2026-11-01-relay-hosting.md`（置き場所の比較）、ADR 0016（端末ごとの鍵。中継の部屋は、使える秘密ごと）。
中継は**実装済み・実機での確認は済み**（トンネル経由）。足りないのは運営の判断。

## 1. 先に答える: 「拒否」と「ブリッジ不在」を分けられるか
- **セキュリティ上は、分けても悪くない。** 部屋の ID は鍵のハッシュ（128 ビット）で、推測できない。分かるのは「この部屋の持ち主は失効した」だけで、すでに持っている人（その端末）にしか意味がない。
- **制約は技術的な作りの問題**。今は、失効すると秘密と一緒に部屋の登録をやめるので、中継は「部屋がない」としか言えない。分けるには、ブリッジが**失効した端末の部屋を登録し続けて、そこに来た接続を「拒否」で返す**必要がある（部屋の ID＝ハッシュは台帳に残す。鍵は消す）。台帳に項目が増え、部屋の数が（16 台まで）少し増える。
- 結論: **文言を 1 つにする（採用。「登録されたブリッジが見つかりません。…動いているか確かめ、動いているのに見つからなければ、ペアリングが解除されたかもしれません」）**。直結・トンネルの住所では、今までどおり「拒否」を見分けて専用の文言を出す。中継でも見分ける実装は、必要になったとき（利用者が中継だけで使い、失効が頻繁になったとき）に足す。

## 2. 分かっていないこと（調べる・決める人つき）

|---|---|---|---|
| 1 | **Anthropic の規約** | 中継自体は、Claude の認証情報や API に**触れない**（暗号化されたフレームを流すだけ。Claude の呼び出しは利用者のパソコンの公式 CLI）。ただし「公式 CLI を、サブスクリプションで、別のアプリの裏から呼ぶ」こと（ADR 0005）が規約に合うか、公開サービスとして中継を運営することが「利用の仲介」に当たらないか、は**まだ確認していない**。この製品全体の前提なので、最優先 | ユーザー（規約の確認と、必要なら Anthropic への問い合わせ） |
| 2 | 運営するか | 公式の中継を運営するか、利用者が自前でトンネルを用意する形だけにするか | ユーザー |

| 5 | 見えるもの・ログ・プライバシー | 中継に見えるのは、部屋の ID・接続元の IP・時刻・通信量。内容（質問・回答・鍵）は見えない（Noise）。**IP をログに残さない／短期だけ残す**を決め、**プライバシーポリシー**に書く（日本語・英語） | ユーザー（方針）／エージェント（文面の草案） |

| 8 | 運営者の持続性 | 個人で運営する場合、止まったときの利用者への影響。**中継の URL は設定で変えられる**ので、自前運営へ移れる。運営をやめるときの告知の仕方を決める | ユーザー |
| 9 | 公開の時期 | 中継を、先に少人数（身近な利用者）だけで試すか | ユーザー |

## 3. 推奨（たたき台）
1. #1 の規約の確認を**最初に**行う（結果しだいで、他の判断が変わる）。
2. 運営する（#2）。ただし**ベストエフォート・無保証**、**IP は保存しない**、**内容は見えない**を明記（#5・#6）。
3. 公開前に VPS へ（#3）。それまでは開発機＋Cloudflare Tunnel（`spellink.uk` のサブドメイン）。
4. 帯域の上限と、アイドル切断を足す（#7。エージェントが実装）。
5. 自前運営の手順書（同じバイナリ）を `docs/guides/` に置き、運営をやめても使い続けられる形にする（#8）。

## 4. エージェントができること（ユーザーの判断を待たずに進められる）
- 帯域の上限・アイドル切断の実装とテスト／systemd ユニットと運営手順書／プライバシーポリシーの草案（日英）／失効した端末の部屋を「拒否」で返す実装（必要になったとき）。
