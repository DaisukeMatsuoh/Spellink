## 残り（運営の中継を広く公開する前に直す）
個人の寄付運営の規模なら当面は許容できる、可用性（止められる）に関する項目。攻撃の手順になるので、細部は、直してから書く。
- 名前サービスの保存と DNS の応答が、同じ排他の中にある（登録が多いと応答が遅れる）。
- TLS の入口に、接続ごとの本体の読み取りの期限と、接続元ごとの同時接続の上限がない。
- Let's Encrypt の枠（週 50 件）の乱用への備え → **対応済み**（ADR 0017 の追記: 45 と 5 の予約、`--infra-ids`）。
- DNS の接続元ごとの制限は、大きな公開リゾルバに不利。
- `--trust-proxy` は、前段（Cloudflare など）の後ろ専用（現在の構成は使わない）。
- コンテナの資源の上限（`cpus`・`ulimits`）とヘルスチェック、ベースイメージの固定。
- ブリッジの管理 API と画面が LAN からも届く（トークン必須）。管理トークンがブラウザの履歴に残る。
- 端末の設計上の限界: ペアリングの鍵は、端末の保存先に平文で置かれる（同じ端末の別アプリが読める）。
- 文字データの生成（`build-glyphs` の実行時だけ）に、ダウンロードの検証が足りない。
- 表示だけの問題: 1 つの `Status.error` を、2 つの機械が上書きし合う。
