## 状態遷移表の書き方
- **縦軸 = 状態、横軸 = イベント、セル = 処理（Action）と遷移先。** ステートマシン図ではなく、全マスを埋めるマトリクス。
- **すべてのマスを埋める。** 起こりえないマスにも `—` と、そう言える**理由**を書く。理由が書けないマスは、起こりうる。
- **イベントは、利用者が考えもしないタイミングで起きる前提**で洗い出す: 連打、処理中の操作、別ノート・別ページへの移動、接続の断、再接続の重複、ブリッジの再起動、遅れて届くフレーム、二重のフレーム、想定外の値。
- セルの書式: `A3→S4`（処理 A3 を行い、状態 S4 へ）。処理は表の下の凡例で定義する。遷移しないときは `A3` だけ。
- 記号: `—` 起こりえない（理由は凡例の注）、`×` 起きるが無視する（理由は注）、`！` **未定義・穴**（現状コードに処理がない）。穴が埋まったら `！` を消す。意図的に後回しにしたものは `（保留）`、テストだけ足りないものは ⬜ と書く。

## 現状の記号（凡例の「現状」列）
- ✅ 実装済みでテストがある
- ⬜ 実装はあるがテストがない、または未対応で、やることが決まっている
- 🟡 実装はあるがテストがない、または推定
- ❌ 未実装（穴）
- ❓ 仕様の判断が要る（ユーザーに確認）
- ⚠ 提案（現状と違う仕様案）

## 実装の方針（表をコードにする）
状態遷移表は、コードの中でも**表の形**にする（ユーザーの C 実装 `SPI_Monitor` と同じ考え方: `[状態][イベント]` に 1 マス 1 処理）。
- TypeScript: `Record<State, Record<Event, Cell>>`。型で全マスを強制する。セルは `{action, next}` の組で、状態の変更は表だけが持つ。
- 範囲外の状態・イベントが来たら、黙って通さず、失敗として止める（元の C 実装は範囲を確認していない）。
- 全マスを順に走らせるテストで、表の穴（セルの欠け、`next` が存在しない状態）を検出する。

## 運用ルール
1. 機能追加・不具合修正は、まず該当の表に、新しい状態・イベント・マスを足して、**仕様として確認してから**コードを書く。
2. すべてのマス（`—` を除く）に、少なくとも 1 つのテストを対応させる（凡例の「テスト」列）。
3. `！` と `❌` が残っている表は、その機能を「完了」と呼ばない。進捗ファイルにも残す。
4. 不具合は、表のどのマスが間違っていたか、または空欄だったかを、ログ（`docs/notes/progress/log/`）に書く。
