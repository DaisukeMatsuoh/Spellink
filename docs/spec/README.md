**コードを書く・変える前に、ここを先に直す。** 表が仕様で、コードとテストは表に従う（ADR 0014）。

## 状態遷移表の書き方
- **縦軸 = 状態、横軸 = イベント、セル = 処理（Action）と遷移先。** ステートマシン図ではなく、全マスを埋めるマトリクス。
- **すべてのマスを埋める。** 起こりえないマスにも `—` と、そう言える**理由**を書く。理由が書けないマスは、起こりうる。
- **イベントは、利用者が考えもしないタイミングで起きる前提**で洗い出す: 連打、処理中の操作、別ノート・別ページへの移動、接続の断、再接続の重複、ブリッジの再起動、遅れて届くフレーム、二重のフレーム、想定外の値。
- セルの書式: `A3→S4`（処理 A3 を行い、状態 S4 へ）。処理は表の下の凡例で定義する。遷移しないときは `A3` だけ。
- 記号: `—` 起こりえない（理由は凡例の注）、`×` 起きるが無視する（理由は注）、`！` **未定義・穴**（現状コードに処理がない）。穴が埋まったら `！` を消す。意図的に後回しにしたものは `（保留）`、テストだけ足りないものは ⬜ と書く。

## 現状の記号（凡例の「現状」列）
- ✅ 実装済みでテストがある
- ⬜ 実装はあるがテストがない、または未対応で、やることが決まっている
- 🟡 実装はあるがテストがない、または推定
- ❌ 未実装（穴）
- ❓ 仕様の判断が要る（ユーザーに確認）
- ⚠ 提案（現状と違う仕様案）

## 実装の方針（表をコードにする）
状態遷移表は、コードでも**表の形**で動かす（ユーザーの C 実装 `SPI_Monitor` と同じ考え方: `[状態][イベント]` に 1 マス 1 処理。状態の変更は 1 か所）。表を後からコードにするのではなく、**表を直せばコードの表が直る**。
- 元データは、`docs/spec/` の文書の表。**端末の質問の流れ（`ask-flow.md`）は実装済み**: `npm run spec`（`plugin/scripts/gen-ask-table.js`）が、文書から `plugin/src/askTable.generated.ts` を作る。全マスが埋まっていない・知らない名前・読めないマスは、場所を示して失敗する。
- 実行側（`plugin/src/askMachine.ts`）は、マスを引いて、遷移先へ移り、処理を呼ぶだけ。処理（ハンドラ）は `AskFlow` に 1 つずつ。表の処理 ID に対応するハンドラがなければ、コンパイルが通らない。
- 表が「起こりえない」としたことが起きたら、記録（`ask.never`）して何も変えない。テストは、この記録が 1 件でもあれば失敗する（どのシナリオでも）。
- テスト（`askMachine.test`）が、文書とコードの表の一致、250 マスすべての動作、遷移の形（終了状態から出ない、全状態に到達できる、全状態から終了できる）を確かめる。
- 手順: ①文書の表（状態・イベント・マス・処理）を直す → ②`npm run spec` → ③足りないハンドラを書く → ④テスト。
- ブリッジの run（`bridge-run.md`）、波線（`wave.md`）、ページ追加（`page-turn.md`）の表は、まだ文書だけ。同じ方法で、順にコードの表にする。

## 運用ルール
1. 機能追加・不具合修正は、まず該当の表に、新しい状態・イベント・マスを足して、**仕様として確認してから**コードを書く。
2. すべてのマス（`—` を除く）に、少なくとも 1 つのテストを対応させる（凡例の「テスト」列）。
3. `！` と `❌` が残っている表は、その機能を「完了」と呼ばない。進捗ファイルにも残す。
4. 不具合は、表のどのマスが間違っていたか、または空欄だったかを、ログ（`docs/notes/progress/log/`）に書く。
