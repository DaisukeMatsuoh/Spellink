# ペアリング: 端末の記録（ブリッジ）と、ペアリングの流れ（プラグイン）

対象: ADR 0016。2 つの状態機械と、その間のフレーム。**この文書の 2 つの表が、コードの表の元データ**（`npm run spec`。生成物は `bridge/internal/devices/table_gen.go` と `plugin/src/pairTable.generated.ts`）。書式は ask-flow.md と同じ（`—` 起こりえない、`×` 起きるが無視する、`！` 穴）。

**実装状況（2026-11-20）**: ブリッジ側（台帳・記録の状態機械・`.snplg` の生成・接続・管理 API・`device` コマンド）とプラグイン側（設定の検査・保存・ペアリングの流れ・画面）は実装済みで、単体テストと、本物のブリッジとの結合テストがある。**実機でのペアリング全体は未確認**。未実装: K を拒否されたときの検出（処理 S10 の呼び出し元。質問の接続の失敗から `keyRefused` を呼ぶ）、ブリッジ側のカメラで QR を読むページ、ペアリング後に端末が自分用のインストーラを消すこと。

## 用語
| 語 | 意味 |
|---|---|
| 記録 | ブリッジの台帳の 1 件。端末 1 台に対応する。`id`（公開してよい 8 バイトの乱数）、名前、世代 `gen`、状態、B、K、時刻 |
| B | 初期の秘密（32 バイトの乱数）。端末専用の `.snplg` に入る。ペアリングにだけ使える |
| K | 本番の秘密（32 バイトの乱数）。ペアリングの成立時に端末へ渡る |
| コード | 端末が作る 8 桁。秘密ではなく、待ち中の要求を選ぶためのもの |
| 要求 | B の通信路でブリッジに届いた `pairRequest{id, gen, code, name}`。ブリッジは、接続・コード・期限を持つ「待ち中の要求」として覚える |
| 窓 | 要求を受け付ける期間。ブリッジは、最初の要求から `windowSec`（既定 90 秒）。入力の失敗の回数は、窓ごとに数える |

## 不変条件
- P1: 1 つの記録について、有効な秘密（B か K）で、**ペアリング以外の質問を処理することはない**のは B だけ（B では質問に答えない）。質問を処理できるのは、状態 Active の K だけ。
- P2: K は、記録が Granted か Active のときだけ存在する。B は、Issued・Requested・Granted のときだけ存在する。Active になった瞬間に、B は台帳から消える（同じ書き込みで）。
- P3: 失効（Revoked）した記録は、B も K も持たない。Revoked から他の状態へは戻らない。
- P4: 台帳への書き込みは、一時ファイルに書いて名前を変える（途中で電源が切れても、古いか新しいかのどちらかが残る）。K を端末へ送る**前**に、Granted の記録（K 入り）を書く。
- P5: 同じコードの要求が 2 つ以上あったら、**どれにも K を渡さない**。
- P7: 処理が失敗したら（台帳の書き込み・読み戻し、乱数、送信）、**状態も記録の中身も、その処理の前に戻す**（巻き戻しは機械の 1 か所）。利用者には失敗を知らせる。例外は P13（失効）: 失敗しても Revoked のまま保ち、接続は閉じたままにして、利用者に「保存できていない」と知らせる。
- P6: タイマーの期限は記録の中に持ち、`Tick` が**いまの状態の期限だけ**を見て、イベントを起こす（状態が変わったら、その期限は消える）。だから、古い通知は作られない。受領の待ちが切れた通知は、記録の `gen` と状態を確かめてから処理する（送信の失敗から来る場合）。時間や回数の帳尻合わせはしない。

## 記録の状態遷移表（ブリッジ。`bridge/internal/devices`）
## 記録: 状態
| 状態 | 意味 |
|---|---|
| NoRecord | その `id` の記録はない |
| Issued | 発行済み。B は有効。まだ要求がない（または窓が閉じた） |
| Requested | 要求を受けた。窓の中で、利用者の確認（コードの入力）を待つ |
| Granted | 利用者が確認した。K を作って送った。端末の受領（ack）を待つ。B と K の両方が有効 |
| Active | 有効。K だけが有効。B は破棄済み |
| Expired | 期限切れ。B は破棄済み（K は作られていない） |
| Revoked | 失効。B も K も破棄済み。記録は監査のために残る |

## 記録: 条件つきのセル
`[more] / [spent]` のセルは、呼ぶ側が**処理の前に**決める条件で、遷移先が変わる。`[more]` は窓が続く（Requested のまま）、`[spent]` は窓が終わる（Issued へ）。
| セル | `[spent]` の条件 |
|---|---|
| Issued または Requested × DeviceRequests（P2） | 同じコードの要求がすでにあり、両方を取り消すと、**待ち中の要求が 1 つも残らない**（要求の上限の超過も、新しい要求を拒否するだけで、状態は変えない `[more]`） |
| Requested × RequestDrops（P5） | その要求を捨てると、待ち中の要求が 1 つも残らない |
| Requested × OwnerMistypes（P7） | この失敗で、窓の入力の失敗が 5 回（`maxAttempts`）に達する |

## 記録: 処理（Action）
| 処理 | 内容 | テスト |
|---|---|---|
| P1 | 記録を作る: `id`（乱数）、`gen=1`、B（乱数 32 バイト）、期限。名前は 1〜64 字、同じ名前は作れない（OwnerAdds を `×d` にする）。台帳は 16 件まで。**台帳へ書き、書けたことを読み戻して確かめる**。端末専用の `.snplg` を作る（`id`、`gen`、B、名前、接続先の一覧、`windowSec`） | ✅ |
| P2 | 要求を覚える（コード、接続、窓の ID）。Requested でなければ窓（ID つき）を始める。**同じコードの要求がすでにあれば、両方を取り消す**（接続は `pair_denied: code_in_use` で閉じる）。要求は 1 つの記録につき最大 4（超えたら新しい要求を `pair_busy` で拒否し、利用者に「複数の要求がある」と知らせる。状態は変えない）。**別の記録に同じコードの要求があるときも、確認（CONFIRM）は曖昧として拒否する**（取り消しは、同じ記録の中だけ） | ✅ |
| P3 | 要求を `pair_denied: grant_pending` で拒否して接続を閉じる（Granted の間は、新しい要求を受けない） | ✅ |
| P5 | その要求を捨てる。要求が 1 つも残らなければ、窓を止める（遷移先は、条件つきのセルで Issued） | ✅ |
| P6 | K（乱数 32 バイト）を作り、**Granted の記録（K 入り）を台帳に書いて読み戻す**。確認できたら、一致した要求の接続へ `pairGrant{K, 接続先}` を送る（台帳の書き込みの後、ロックの外で）。ほかの要求は `pair_denied: superseded` で閉じる。ACK_TIMEOUT を始める。**送れなかったら、ACK_TIMEOUT を自分に入れ直す**（K を消して Issued へ。P11） | ✅ |
| P7 | 失敗を数える（窓の ID ごと）。5 回に達したら、P8 と同じに窓を閉じる（遷移先は、条件つきのセルで Issued）。足りなければ Requested のまま。利用者が、コードを入力した端末の名前ではなく、**入力が拒否されたこと**だけを知る（どの端末が待っているかを、入力した人以外に教えない） | ✅ |
| P8 | すべての要求を `pair_denied: window_closed` で閉じる。TTL がすでに切れていれば、`TtlEnds` を自分に入れ直す（Issued で P12→Expired） | ✅ |
| P9 | K が渡ったと確認できた（`pairAck`、または K での接続）。**B を消して Active の記録を台帳に書き、読み戻す**。要求の接続を閉じる。CONN_K のときは、そのまま質問を受ける（P10） | ✅ |
| P10 | 通常の接続として扱う。最終接続時刻を更新する（書き込みは間引く） | ✅ |
| P11 | 受領が来なかった: K を消し、B は残す。TTL がすでに切れていれば、`TtlEnds` を自分に入れ直す（Issued で P12→Expired） | ✅ |
| P12 | B を消す。待ち中の要求を `pair_denied: expired` で閉じる | ✅ |
| P13 | B と K を消し、その記録の接続をすべて閉じ、中継の部屋の登録を外す。Revoked と時刻を書く。書けなければ、**接続を先に閉じ**、記録を失敗として利用者に知らせる（失効は、利用者が見えるまで残る） | ✅ |
| P14 | `gen` を 1 つ進め、B を作り直し、期限をやり直す。K は消す。その記録の接続をすべて閉じる。新しい `.snplg` を作る | ✅ |
| P15 | 台帳を読み込み、**記録ごとに検証する**（`id`・名前・状態・B と K の有無が状態と矛盾しない・長さ・`gen`）。不正な記録は読み込まず、記録する。要求は覚えていないので、Requested は Issued になる（Granted は K 入りで書かれているので Granted のまま。受領の待ちをやり直す）。B・K の有無の矛盾（例: Active に B が残る）は、**B を捨てて Active として読む**（K があれば）か、読み込まない（K がなければ） | ✅ |
| P17 | 記録を台帳から削除する。 | ✅ |
| P18 | **状態を変えずに**、同じ `id`・`gen` の `.snplg` を作り直す（最新のプラグインに、接続設定を足す）。B が有効な状態（Issued・Requested・Granted）では B 入り、Active では **B なし**（接続設定だけ。K は端末に保存済みで、パッケージには入れない）。台帳は書き換えない | ✅ |

## 記録: 注（`—` と `×` の理由）
- a: 記録がない `id` への B / K の通信路は、**記録の層に届く前**に接続の層が拒否する（`unknown_device`）。ACK も同じ接続からしか来ない。
- b: 要求がない状態で、要求の接続は存在しない。
- c: 記録がない `id` への操作。CLI が「その端末はない」と答え、状態機械には渡さない。
- d: 同じ名前の追加は CLI が拒否する（記録は変わらない）。名前は一意。
- e: 確認する要求がない（Requested 以外）。CLI が「コードを出している端末はない」と答える。Granted は「確認済み」、Active は「ペアリング済み」と答える。
- f: 受領の通知は、Granted でだけ意味がある。ほかの状態で来たら無視し、記録する（遅れた・重複したフレーム）。
- g: その状態では、K はまだ作られていない・すでに破棄されている。K の Noise の握手が通らないので、接続の層が拒否する。
- h: Granted の間に、要求の接続が切れても、K はすでに端末へ送られている可能性がある。AckTimesOut か、K での接続（P9）で決まる。
- i: B はすでに破棄されている（Active）か、期限切れ（Expired）か、失効した（Revoked）。B の握手が通らないので、接続の層が拒否する。
- j: 有効な端末の接続が切れるのは通常のこと。記録の状態は変わらない。
- k: 記録がないので、タイマーも走っていない。
- l: 記録がなければ、読み込むものがない。
- m: タイマーの期限は、その状態にいるときだけ記録に持つ（P6）。ほかの状態に WindowEnds・AckTimesOut・TtlEnds が届くことは、実際にはない（`Tick` が作らない）。届いても何も変えない。
- n: 失効しないと削除できない（誤って有効な端末を消さない）。Expired と Revoked だけ削除できる。
- o: Granted の間に TtlEnds が来ても、受領を待つ。結果は、P9（Active になる）か P11（TtlEnds を見て Expired か Issued）で決まる。
- p: すでに失効している。CLI が「すでに失効」と答える。
- q: 失効した端末は再発行も作り直しもできない。新しい記録（OwnerAdds）を作る。
- r: 期限切れで B は破棄済み。OwnerReissues（新しい B）で作り直す。
- 秘密と通信路: B・K のどちらも、台帳の外（ログ・診断・エラー文・QR・画面）に出さない。`id` と名前は出してよい。

## 記録: 代替（K を端末に保存できない場合）
P6 で K を作らず、P9 で B を消さない（Active でも B が有効）。`gen` は同じ。ほかの表は変わらない。**B が長期の秘密になるので、`.snplg` の漏れが、そのまま端末の漏れになる**（ADR 0016 の 8）。

## 端末の状態遷移表（プラグイン。`plugin/src/pairing*.ts`）
## 端末: 保存するもの（`MyStyle` の下のディレクトリ名。ADR 0016 の 8。削除しない）
| 名前 | 中身 | 使い方 |
|---|---|---|
| `k-<id>-<gen>-<K>` | K（base64url 43 字）。`id` は 16 桁の 16 進 | 同じ `id`・`gen` の名前が 1 つだけなら有効。複数あれば「曖昧」で使わない（K は 1 つの `gen` に 1 つしか作らない） |
| `e-<id>-<gen>-<接続先>` | ブリッジの名前と接続先: `{"n":"名前","u":["wss://…"]}`（`wss://` の URL を最大 4 件）を base64url にしたもの。名前は 255 バイトに収まる分だけ | K と同じ `id`・`gen` のもの。複数あれば、ブリッジが `pairGrant` で渡した 1 つだけなので、複数あれば曖昧として使わない |
- 保存される内容は、すべて**読み出すときに検証する**（形・長さ・個数）。壊れた名前は無視して記録する。
- **パッケージを入れ替えても（更新・再インストール）残る**。実機: seedC のパッケージから、接続設定のない新しいビルドに入れ替えた後も、保存した名前が残り、再起動をまたいでも完全一致で読めた（2026-11-20）。

## 端末: 起動時の初期状態
接続設定の出どころは、**パッケージ（B のペアリング用）か、端末の保存（K の通常用）**。更新で、接続設定のない公開用の `.snplg` を入れても、保存があれば動く。**ブリッジは `id` ごとに独立**に評価する（同じ端末に複数のブリッジを入れられる）。端末は、ブリッジごとに 1 つの状態を持つ（`bridges(パッケージ, 保存)` が、`id` の一覧と、各 `id` の初期状態を返す）。
パッケージの接続設定に `id` があれば、その `id` は一覧に入る。保存に有効な K（と接続先）がある `id` も、一覧に入る。**一覧が空なら、端末全体の画面は NoSetup**（案内）。
| # | その `id` のパッケージの接続設定 | その `id` の保存（K と接続先） | 初期状態 |
|---|---|---|---|
| 1 | （どの `id` も、パッケージも保存もない） | — | 端末全体で NoSetup（案内を出す） |
| 2 | なし | 有効（K と接続先が 1 つずつ） | **Paired**（更新後も、そのまま使える） |
| 3 | なし | 壊れている・曖昧・K だけ・接続先だけ | その `id` は一覧に入れない（「ペアリングし直してください」を出し、壊れた名前は記録する） |
| 4 | あり | なし | Unpaired |
| 5 | あり | 有効で、`gen` がパッケージと一致 | Paired（B は使わない。ブリッジは B をすでに捨てている） |
| 6 | あり | 有効だが、`gen` が違う（再発行された） | Unpaired（古い K は使わない。名前は残る） |
| 7 | あり | 壊れている・曖昧 | Unpaired（記録する） |
- 別の `id` どうしは、互いに影響しない。パッケージを入れ替えると、新しいパッケージの `id` が Unpaired で加わり、前のパッケージの `id` は、保存があれば Paired のまま残る（パッケージの B は端末に残らないが、保存は残る）。
- 質問のときに使うブリッジは、Paired の `id` のうち、`bridgeClient` が全 URL に並列に接続して先に応答した 1 つ（今のコードの、複数のブリッジの扱いのとおり）。
- 保存された K の読み出し: `MyStyle` の一覧から、`k-` で始まる名前だけを見て、上の規則で検証する。
- 接続設定（`__SPELLINK_PAIR__`）は使う前に検証する: `id` 16 桁の 16 進、`gen` 正の整数、B は 32 バイトの文字列表現、名前 1〜64 字、URL は `wss://` のみ最大 8 件、`windowSec` 10〜600（範囲外は既定の 90）。不正なら「なし」として扱い、診断に理由を出す。

## 端末: 状態
| 状態 | 意味 |
|---|---|
| NoSetup | 接続設定がない（公開用のプラグイン）。案内を出す |
| Unpaired | B だけを持つ。ペアリングの前 |
| Connecting | 「ペアリング」を押した。B でブリッジに接続している最中 |
| ShowingCode | ペアリングモード。コードと QR を表示し、ブリッジの確認を待つ。残り時間を表示 |
| Storing | K を受け取った。保存している最中 |
| Paired | K を持つ。質問のときは K で接続する |

## 端末: イベント
| イベント | 意味 |
|---|---|
| UserTapsPair | 利用者が「ペアリング」を押した |
| Connected | B の通信路が成立し、`pairRequest` を送った（コードは、この時に作る） |
| KeyGranted | 検証に通った `pairGrant{K}` が届いた（K は 32 バイト） |
| StoreSucceeds | K の保存が成功し、**読み戻して一致を確かめた** |
| StoreFails | K の保存が失敗した、または読み戻しが一致しない |
| WindowEnds | 残り時間が 0 になった（`windowSec`。窓の ID つき） |
| Disconnected | 接続が切れた、または接続に失敗した（時間切れを含む） |
| Denied | `pairDenied`（理由つき）が届いた |
| UserCancels | 利用者が「やめる」を押した、またはプラグインの画面を離れた |
| KeyRefused | 質問のときの K の接続を、ブリッジが拒否した（失効・再発行・世代の不一致） |
| BannerArrives | ブリッジが、頼んだ文言を手書きにして送ってきた（`pairBanner`。画面の飾り。なくても動く） |

## 端末: 処理（Action）
| 処理 | 内容 | テスト |
|---|---|---|
| S1 | 接続設定の検証済みの値で、B の通信路（Noise）を張り始める（時間切れつき。URL は全部に並列）。「ペアリング」ボタンを無効にし、進捗を出す。窓の ID（通し番号）を作る | ✅ |
| S2 | コード（8 桁。乱数）を作り、`pairRequest{id, gen, code, name}` を送り、**画面にコード・QR・残り時間を出す**。QR の中身は `spellink://pair?v=1&i=<id>&c=<code>`（B・K は含まない）。窓のタイマー（`windowSec`。既定 90 秒）を始める | ✅ |
| S3 | `pairGrant` の K と接続先を受け取る（検証済み）。2 つの名前（`k-…`、`e-…`）を保存し始める。窓のタイマーを止める | ✅ |
| S4 | `pairAck` を送る。接続を閉じる。画面に「ペアリング済み」を出す。**成功は結果で確かめる**: 保存した K と接続先を読み戻して、**両方**一致している（STORE_OK の条件）。保存は、`MyStyle/Spellink-pairing/` の下に `k-<id>-<gen>-<K>` と `e-<id>-<gen>-<接続先>` というディレクトリを `makeDir` で作り、`listFiles` で読み戻す。**削除はしない**（ADR 0016 の 8）。すでに同じ名前があれば、作らずに読み戻して一致を確かめる | ✅ |
| S5 | 保存に失敗: 接続を閉じ（`pairAck` は送らない）、メモリの K を消し、利用者に失敗を知らせる。ブリッジは AckTimesOut で I に戻る | ✅ |
| S6 | 窓が終わった: 接続を閉じ、画面に「時間切れ」を出す。窓の ID が古い通知は無視する | ✅ |
| S7 | 接続の失敗・断: 画面に理由を出す。再試行はしない（利用者がもう一度押す） | ✅ |
| S8 | `pairDenied` の理由（`code_in_use`、`pair_busy`、`grant_pending`、`window_closed`、`expired`、`superseded`、`unknown_device`）を、利用者向けの文言で出す | ✅ |
| S9 | 接続を閉じ、タイマーを止め、画面を戻す | ✅ |
| S10 | 保存された K を、メモリ上で使えないとして扱い（消せないかもしれない。`gen` が違えば、次回から無視される）、B のペアリングを案内する。「ペアリングし直してください」を出す | ✅ |
| S11 | 手書きの飾りを受け取った: 検証に通れば（線の数・点の数・座標の範囲）画面に出す。通らなければ捨てて記録する（飾りがなくても、画面は文字で出る）。**保存先には何も書かない** | ✅ |

## 端末: 注
- a: NoSetup では「ペアリング」ボタン自体を出さず、案内（「ブリッジで『端末を追加』をして、専用の `.snplg` を入れてください」）を出す。押せない。
- b: その状態では、そのイベントを起こす接続・保存がない。
- c: 二重押下。ボタンは、Unpaired・Paired 以外で無効だが、押されても何も変えない（連打対策）。
- d: 要求を送る前に KeyGranted が来ることはない。来たら検証に通らない（受け取らない）。記録する。
- e: CONNECTED は 1 回の接続につき 1 回。重複して来たら無視する。
- f: 保存の最中に、2 つ目の KeyGranted が来た（重複フレーム）。無視する（K は 1 つしか受け取らない）。
- g: その状態では、タイマーも接続もない。窓の ID が古い通知は、状態に関係なく無視する。
- h: やめる操作はあるが、何もしていない状態なので変えない。
- i: K での接続は Paired でしか行わない。ほかでは K を使わない。
  - KeyRefused の検出（実装）: 質問の接続（`connectFirst`）が、**ペアリング済みのブリッジのすべての住所で失敗し、その 1 つ以上が `unauthorized` / `device_removed`（ブリッジが端末を断るときの理由）だった**ときに、そのブリッジを「拒否された」と判断し、利用者に「ペアリングし直してください」を出す（質問の画面と設定画面）。状態は保存せず、毎回判断する（再ペアリングで K が新しくなれば、次の接続から通る）。**中継経由だけの住所では、拒否と「ブリッジが不在」の区別がつかない**（中継は、部屋がなければ接続を断るだけ）ので、検出できない。
- j: 保存の最中に窓が終わる・接続が切れる・拒否される。K を受け取った後は、窓も接続も関係がなく、保存の結果（StoreSucceeds / StoreFails）で決まる。ブリッジ側は ACK_TIMEOUT で決める。
- k: 保存の最中に画面を離れても、保存は中断しない（途中で止めると K が半端になる）。完了後に Paired になる。
- l: 質問の接続の断は、AskFlow が扱う（ask-flow.md）。ペアリングの状態は変えない。
- m: K での接続のとき `pairDenied` は来ない（拒否は KeyRefused）。
- o: 鍵を受け取った後に届いた飾りの文字。もう画面に出さないので捨てる。
- **端末が B を持つのは、K を受け取るまで**。B は `.snplg` の中に残り続けるが、ブリッジが破棄済みなので、使えない（Paired のとき、B は使わない）。

## ペアリングのフレーム（`docs/spec/interfaces.md` の I22〜I27）
| フレーム | 向き | 中身 | 検証 |
|---|---|---|---|
| `pairRequest` | 端末→ブリッジ（B の通信路） | `id`、`gen`、`code`（8 桁の数字）、`banner`（任意。手書きにしてほしい文言。1〜120 字）、`layout`（`banner` があるとき。文字の大きさと幅） | 型・長さ。`id`/`gen` が接続の記録と一致。コードは数字 8 桁のみ。`banner` は長さ、`layout` は既存の検査（`ValidLayout`）。不正な `banner` は、ペアリングを失敗にせず無視する |
| `pairBanner` | ブリッジ→端末（B の通信路。`pairRequest` が受け付けられた後だけ） | `strokes`（頼んだ文言を、ブリッジの手書きの字で書いた線。最大 3000 本） | 端末が検証: 線の数・点の数・座標（`line` フレームと同じ上限）。不正なら、線なしの飾りとして扱い、画面は文字で出す |
| `pairGrant` | ブリッジ→端末（B の通信路） | `key`（K。32 バイトを base64url）、`endpoints`（`wss://` の URL、最大 4 件。保存できる長さに収まるもの） | 端末が検証: K の長さ・文字種、URL の形・個数・長さ（保存できない長さなら、受け取らない） |
| `pairAck` | 端末→ブリッジ（B の通信路） | `id`、`gen` | 記録が G で、`gen` が一致 |
| `pairDenied` | ブリッジ→端末（B の通信路） | `reason`（上の 7 種のどれか） | 端末が検証: 既知の理由。未知の理由は「拒否されました」とだけ出す |
- どのフレームも、古いブリッジ・端末では `bad_request`（未知の型）で失敗する形（ADR 0013 の教訓）。
- B の通信路で許すフレームは、この 5 種と `hello`・`ping` だけ。**質問（`ask`）などは、B の通信路では受け付けない**（P1）。

## テストの対応（実装時）
- 記録の表は、105 マスすべて（`—` は「起きないことの確認」）を、記録の状態機械のテスト（`devices_test.go`）で、全マス総当たりで確かめる。台帳の読み込みは、壊れた記録、状態と B・K の矛盾、途中の電源断（一時ファイルだけが残る）を確かめる。
- 端末の表は、60 マス（`pairingMachine.test`）。保存の失敗と読み戻しの不一致、窓の ID が古い通知、二重押下、重複した KeyGranted を含む。
- 結合テスト: 本物のブリッジと端末のコードで、発行 → B で接続 → コードの入力 → K を受け取る → B の拒否 → K での質問、失効後の拒否、再発行後の旧 K の拒否。
