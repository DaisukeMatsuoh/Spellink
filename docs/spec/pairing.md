# ペアリング: 端末の記録（ブリッジ）と、ペアリングの流れ（プラグイン）（提案・確認待ち）

対象: ADR 0016。2 つの状態機械と、その間のフレーム。**この表を確認してから、コードを書く**（ADR 0014）。書式は ask-flow.md と同じ（`—` 起こりえない、`×` 起きるが無視する、`！` 穴）。

## 用語
| 語 | 意味 |
|---|---|
| 記録 | ブリッジの台帳の 1 件。端末 1 台に対応する。`id`（公開してよい 8 バイトの乱数）、名前、世代 `gen`、状態、B、K、時刻 |
| B | 初期の秘密（32 バイトの乱数）。端末専用の `.snplg` に入る。ペアリングにだけ使える |
| K | 本番の秘密（32 バイトの乱数）。ペアリングの成立時に端末へ渡る |
| コード | 端末が作る 8 桁。秘密ではなく、待ち中の要求を選ぶためのもの |
| 要求 | B の通信路でブリッジに届いた `pairRequest{id, gen, code, name}`。ブリッジは、接続・コード・期限を持つ「待ち中の要求」として覚える |
| 窓 | 要求を受け付ける期間。ブリッジは、最初の要求から `windowSec`（既定 90 秒）。窓には ID（通し番号）が付く |

## 不変条件
- P1: 1 つの記録について、有効な秘密（B か K）で、**ペアリング以外の質問を処理することはない**のは B だけ（B では質問に答えない）。質問を処理できるのは、状態 A の K だけ。
- P2: K は、記録が G か A のときだけ存在する。B は、I・Q・G のときだけ存在する。A になった瞬間に、B は台帳から消える（同じ書き込みで）。
- P3: 失効（R）した記録は、B も K も持たない。R から他の状態へは戻らない。
- P4: 台帳への書き込みは、一時ファイルに書いて名前を変える（途中で電源が切れても、古いか新しいかのどちらかが残る）。K を端末へ送る**前**に、G の記録（K 入り）を書く。
- P5: 同じコードの要求が 2 つ以上あったら、**どれにも K を渡さない**。
- P6: タイマーの通知は、窓の ID または記録の `gen` と状態の組で識別する。古い通知は無視する（時間や回数の帳尻合わせはしない）。

## A. ブリッジ: 記録の状態遷移表（`bridge/internal/devices`）
### 状態
| 状態 | 意味 |
|---|---|
| N | その `id` の記録はない |
| I | 発行済み。B は有効。まだ要求がない（または窓が閉じた） |
| Q | 要求を受けた。窓の中で、利用者の確認（コードの入力）を待つ |
| G | 利用者が確認した。K を作って送った。端末の受領（ack）を待つ。B と K の両方が有効 |
| A | 有効。K だけが有効。B は破棄済み |
| X | 期限切れ。B は破棄済み（K は作られていない） |
| R | 失効。B も K も破棄済み。記録は監査のために残る |

### イベント
| イベント | 意味 |
|---|---|
| ISSUE | 利用者が「端末を追加」（新しい名前） |
| CONN_B | B の通信路（Noise）が成立し、検証に通った `pairRequest` が届いた |
| DISCONNECT | 待ち中の要求の接続が切れた |
| CONFIRM_OK | 利用者が入力したコードが、待ち中の要求の**ちょうど 1 つ**に一致した（QR を読んだ場合も同じ） |
| CONFIRM_BAD | 利用者が入力したコードが、どれにも一致しない、または複数に一致する（P5） |
| ACK | 端末から `pairAck`（B の通信路）が届いた |
| CONN_K | K の通信路が成立した |
| WINDOW | 窓の終わり（窓の ID つき） |
| ACK_TIMEOUT | 受領の待ちが切れた（既定 30 秒。`gen` と状態つき） |
| TTL | 発行の期限（既定 24 時間）が切れた |
| REVOKE | 利用者が「失効」 |
| REISSUE | 利用者が「再発行」（新しい `.snplg`。`gen` を 1 つ進める） |
| REPACK | 利用者が「`.snplg` の作り直し」（同じ `id`・`gen`。秘密は変えない。プラグインの更新や、`.snplg` をなくしたとき） |
| RESTART | ブリッジが起動し、台帳を読み込んだ |
| FORGET | 利用者が記録を削除 |

### 処理（Action）
| 処理 | 内容 | テスト |
|---|---|---|
| P1 | 記録を作る: `id`（乱数）、`gen=1`、B（乱数 32 バイト）、期限。名前は 1〜64 字、同じ名前は作れない（ISSUE を `×d` にする）。台帳は 16 件まで。**台帳へ書き、書けたことを読み戻して確かめる**。端末専用の `.snplg` を作る（`id`、`gen`、B、名前、接続先の一覧、`windowSec`） | ⬜ |
| P2 | 要求を覚える（コード、接続、窓の ID）。Q でなければ窓を始める。**同じコードの要求がすでにあれば、両方を取り消す**（P5。接続は `pair_denied: code_in_use` で閉じる）。要求は 1 つの記録につき最大 4（超えたら新しい要求を `pair_busy` で拒否し、利用者に「複数の要求がある」と知らせる） | ⬜ |
| P3 | 要求を `pair_denied: grant_pending` で拒否して接続を閉じる（G の間は、新しい要求を受けない） | ⬜ |
| P5 | その要求を捨てる。要求がなくなれば窓を止めて I へ | ⬜ |
| P6 | K（乱数 32 バイト）を作り、**G の記録（K 入り）を台帳に書いて読み戻す**。確認できたら、一致した要求の接続へ `pairGrant{K}` を送る。ほかの要求は `pair_denied: superseded` で閉じる。ACK_TIMEOUT を始める。送れなければ（SEND_FAIL）、K を消して I へ | ⬜ |
| P7 | 失敗を数える（窓の ID ごと）。5 回に達したら、P8 と同じ（窓を閉じる）。足りなければ Q のまま | ⬜ |
| P8 | すべての要求を `pair_denied: window_closed` で閉じる。TTL が切れていなければ I、切れていれば X | ⬜ |
| P9 | K が渡ったと確認できた（`pairAck`、または K での接続）。**B を消して A の記録を台帳に書き、読み戻す**。要求の接続を閉じる。CONN_K のときは、そのまま質問を受ける（P10） | ⬜ |
| P10 | 通常の接続として扱う。最終接続時刻を更新する（書き込みは間引く） | ⬜ |
| P11 | 受領が来なかった: K を消し、B は残す。TTL が切れていれば X、そうでなければ I | ⬜ |
| P12 | B を消す。待ち中の要求を `pair_denied: expired` で閉じる | ⬜ |
| P13 | B と K を消し、その記録の接続をすべて閉じ、中継の部屋の登録を外す。R と時刻を書く。書けなければ、**接続を先に閉じ**、記録を失敗として利用者に知らせる（失効は、利用者が見えるまで残る） | ⬜ |
| P14 | `gen` を 1 つ進め、B を作り直し、期限をやり直す。K は消す。その記録の接続をすべて閉じる。新しい `.snplg` を作る | ⬜ |
| P15 | 台帳を読み込み、**記録ごとに検証する**（`id`・名前・状態・B と K の有無が状態と矛盾しない・長さ・`gen`）。不正な記録は読み込まず、記録する。要求は覚えていないので、Q は I になる（G は K 入りで書かれているので G のまま。受領の待ちをやり直す）。B・K の有無の矛盾（例: A に B が残る）は、**B を捨てて A として読む**（K があれば）か、読み込まない（K がなければ） | ⬜ |
| P17 | 記録を台帳から削除する。 | ⬜ |
| P18 | **状態を変えずに**、同じ `id`・`gen` の `.snplg` を作り直す（最新のプラグインに、接続設定を足す）。B が有効な状態（I・Q・G）では B 入り、A では **B なし**（接続設定だけ。K は端末に保存済みで、パッケージには入れない）。台帳は書き換えない | ⬜ |

### 注（`—` と `×` の理由）
- a: 記録がない `id` への B / K の通信路は、**記録の層に届く前**に接続の層が拒否する（`unknown_device`）。ACK も同じ接続からしか来ない。
- b: 要求がない状態で、要求の接続は存在しない。
- c: 記録がない `id` への操作。CLI が「その端末はない」と答え、状態機械には渡さない。
- d: 同じ名前の追加は CLI が拒否する（記録は変わらない）。名前は一意。
- e: 確認する要求がない（Q 以外）。CLI が「コードを出している端末はない」と答える。G は「確認済み」、A は「ペアリング済み」と答える。
- f: 受領の通知は、G でだけ意味がある。ほかの状態で来たら無視し、記録する（遅れた・重複したフレーム）。
- g: その状態では、K はまだ作られていない・すでに破棄されている。K の Noise の握手が通らないので、接続の層が拒否する。
- h: G の間に、要求の接続が切れても、K はすでに端末へ送られている可能性がある。ACK_TIMEOUT か、K での接続（P9）で決まる。
- i: B はすでに破棄されている（A）か、期限切れ（X）か、失効した（R）。B の握手が通らないので、接続の層が拒否する。
- j: 有効な端末の接続が切れるのは通常のこと。記録の状態は変わらない。
- k: 記録がないので、タイマーも走っていない。
- l: 記録がなければ、読み込むものがない。
- m: タイマーは、窓の ID（WINDOW）または `gen` と状態（ACK_TIMEOUT、TTL）で識別する。状態が変わった後に届いた古い通知は無視する（P6）。
- n: 失効しないと削除できない（誤って有効な端末を消さない）。X と R だけ削除できる。
- o: G の間に TTL が切れても、受領を待つ。結果は、P9（A になる）か P11（TTL を見て X か I）で決まる。
- p: すでに失効している。CLI が「すでに失効」と答える。
- q: 失効した端末は再発行も作り直しもできない。新しい記録（ISSUE）を作る。
- r: 期限切れで B は破棄済み。REISSUE（新しい B）で作り直す。
- 秘密と通信路: B・K のどちらも、台帳の外（ログ・診断・エラー文・QR・画面）に出さない。`id` と名前は出してよい。

### 代替（K を端末に保存できない場合）
P6 で K を作らず、P9 で B を消さない（A でも B が有効）。`gen` は同じ。ほかの表は変わらない。**B が長期の秘密になるので、`.snplg` の漏れが、そのまま端末の漏れになる**（ADR 0016 の 8）。

## B. プラグイン: ペアリングの流れの状態遷移表（`plugin/src/pairing*.ts`）
### 端末に保存するもの（`MyStyle` の下のディレクトリ名。ADR 0016 の 8。削除しない）
| 名前 | 中身 | 使い方 |
|---|---|---|
| `k-<id>-<gen>-<K>` | K（base64url 43 字）。`id` は 16 桁の 16 進 | 同じ `id`・`gen` の名前が 1 つだけなら有効。複数あれば「曖昧」で使わない（K は 1 つの `gen` に 1 つしか作らない） |
| `e-<id>-<gen>-<接続先>` | 接続先の一覧（`wss://` の URL を最大 4 件、JSON を base64url にしたもの。名前は 255 バイトに収まる分だけ） | K と同じ `id`・`gen` のもの。複数あれば、**ブリッジが `pairGrant` で渡した 1 つだけ**なので、曖昧として使わない |
- 保存される内容は、すべて**読み出すときに検証する**（形・長さ・個数）。壊れた名前は無視して記録する。
- **パッケージを入れ替えても（更新・再インストール）残る**。実機: seedC のパッケージから、接続設定のない新しいビルドに入れ替えた後も、保存した名前が残り、再起動をまたいでも完全一致で読めた（2026-11-20）。

### 起動時の初期状態（イベントではなく、関数 `initial`）
接続設定の出どころは、**パッケージ（B のペアリング用）か、端末の保存（K の通常用）**。更新で、接続設定のない公開用の `.snplg` を入れても、保存があれば動く。
| # | パッケージの接続設定 | 保存（K と接続先） | 初期状態 |
|---|---|---|---|
| 1 | なし（公開用の `.snplg`） | なし | U0（案内を出す） |
| 2 | なし | 有効（K と接続先が 1 つずつ） | **U5**（更新後も、そのまま使える） |
| 3 | なし | 壊れている・曖昧・K だけ・接続先だけ | U0（「ペアリングし直してください」を出す。壊れた名前は記録） |
| 4 | あり | なし | U1 |
| 5 | あり | 有効で、`id` と `gen` がパッケージと一致 | U5（B は使わない。ブリッジは B をすでに捨てている） |
| 6 | あり | 有効だが、`id` が違う | （保留）別のブリッジ。複数のブリッジは、この表の範囲外。当面は U1 とし、保存はそのまま残す |
| 7 | あり | 有効だが、`gen` が違う（再発行された） | U1（古い K は使わない。名前は残る） |
| 8 | あり | 壊れている・曖昧 | U1（記録する） |
- 保存された K の読み出し: `MyStyle` の一覧から、`k-` で始まる名前だけを見て、上の規則で検証する。
- 接続設定（`__SPELLINK_PAIR__`）は使う前に検証する: `id` 16 桁の 16 進、`gen` 正の整数、B は 32 バイトの文字列表現、名前 1〜64 字、URL は `wss://` のみ最大 8 件、`windowSec` 10〜600（範囲外は既定の 90）。不正なら「なし」として扱い、診断に理由を出す。

### 処理（Action）
| 処理 | 内容 | テスト |
|---|---|---|
| S1 | 接続設定の検証済みの値で、B の通信路（Noise）を張り始める（時間切れつき。URL は全部に並列）。「ペアリング」ボタンを無効にし、進捗を出す。窓の ID（通し番号）を作る | ⬜ |
| S2 | コード（8 桁。乱数）を作り、`pairRequest{id, gen, code, name}` を送り、**画面にコード・QR・残り時間を出す**。QR の中身は `spellink://pair?v=1&i=<id>&c=<code>`（B・K は含まない）。窓のタイマー（`windowSec`。既定 90 秒）を始める | ⬜ |
| S3 | `pairGrant` の K と接続先を受け取る（検証済み）。2 つの名前（`k-…`、`e-…`）を保存し始める。窓のタイマーを止める | ⬜ |
| S4 | `pairAck` を送る。接続を閉じる。画面に「ペアリング済み」を出す。**成功は結果で確かめる**: 保存した K と接続先を読み戻して、**両方**一致している（STORE_OK の条件）。保存は、`MyStyle` の下に `k-<id>-<gen>-<K>` と `e-<id>-<gen>-<接続先>` というディレクトリを `makeDir` で作り、`listFiles` で読み戻す。**削除はしない**（ADR 0016 の 8）。すでに同じ名前があれば、作らずに読み戻して一致を確かめる | ⬜ |
| S5 | 保存に失敗: 接続を閉じ（`pairAck` は送らない）、メモリの K を消し、利用者に失敗を知らせる。ブリッジは ACK_TIMEOUT で I に戻る | ⬜ |
| S6 | 窓が終わった: 接続を閉じ、画面に「時間切れ」を出す。窓の ID が古い通知は無視する | ⬜ |
| S7 | 接続の失敗・断: 画面に理由を出す。再試行はしない（利用者がもう一度押す） | ⬜ |
| S8 | `pairDenied` の理由（`code_in_use`、`pair_busy`、`grant_pending`、`window_closed`、`expired`、`superseded`、`unknown_device`）を、利用者向けの文言で出す | ⬜ |
| S9 | 接続を閉じ、タイマーを止め、画面を戻す | ⬜ |
| S10 | 保存された K を、メモリ上で使えないとして扱い（消せないかもしれない。`gen` が違えば、次回から無視される）、B のペアリングを案内する。「ペアリングし直してください」を出す | ⬜ |

### 注
- a: U0 では「ペアリング」ボタン自体を出さず、案内（「ブリッジで『端末を追加』をして、専用の `.snplg` を入れてください」）を出す。押せない。
- b: その状態では、そのイベントを起こす接続・保存がない。
- c: 二重押下。ボタンは、U1・U5 以外で無効だが、押されても何も変えない（連打対策）。
- d: 要求を送る前に GRANT が来ることはない。来たら検証に通らない（受け取らない）。記録する。
- e: CONNECTED は 1 回の接続につき 1 回。重複して来たら無視する。
- f: 保存の最中に、2 つ目の GRANT が来た（重複フレーム）。無視する（K は 1 つしか受け取らない）。
- g: その状態では、タイマーも接続もない。窓の ID が古い通知は、状態に関係なく無視する。
- h: やめる操作はあるが、何もしていない状態なので変えない。
- i: K での接続は U5 でしか行わない。ほかでは K を使わない。
- j: 保存の最中に窓が終わる・接続が切れる・拒否される。K を受け取った後は、窓も接続も関係がなく、保存の結果（STORE_OK / STORE_FAIL）で決まる。ブリッジ側は ACK_TIMEOUT で決める。
- k: 保存の最中に画面を離れても、保存は中断しない（途中で止めると K が半端になる）。完了後に U5 になる。
- l: 質問の接続の断は、AskFlow が扱う（ask-flow.md）。ペアリングの状態は変えない。
- m: K での接続のとき `pairDenied` は来ない（拒否は K_REFUSED）。
- **端末が B を持つのは、K を受け取るまで**。B は `.snplg` の中に残り続けるが、ブリッジが破棄済みなので、使えない（U5 のとき、B は使わない）。

## C. ペアリングのフレーム（`docs/spec/interfaces.md` の I22〜I27）
| フレーム | 向き | 中身 | 検証 |
|---|---|---|---|
| `pairRequest` | 端末→ブリッジ（B の通信路） | `id`、`gen`、`code`（8 桁の数字）、`name`（1〜64 字） | 型・長さ。`id`/`gen` が接続の記録と一致。コードは数字 8 桁のみ |
| `pairGrant` | ブリッジ→端末（B の通信路） | `key`（K。32 バイトを base64url）、`endpoints`（`wss://` の URL、最大 4 件。保存できる長さに収まるもの） | 端末が検証: K の長さ・文字種、URL の形・個数・長さ（保存できない長さなら、受け取らない） |
| `pairAck` | 端末→ブリッジ（B の通信路） | `id`、`gen` | 記録が G で、`gen` が一致 |
| `pairDenied` | ブリッジ→端末（B の通信路） | `reason`（上の 7 種のどれか） | 端末が検証: 既知の理由。未知の理由は「拒否されました」とだけ出す |
- どのフレームも、古いブリッジ・端末では `bad_request`（未知の型）で失敗する形（ADR 0013 の教訓）。
- B の通信路で許すフレームは、この 4 種と `hello`・`ping` だけ。**質問（`ask`）などは、B の通信路では受け付けない**（P1）。

## テストの対応（実装時）
- A の表は、105 マスすべて（`—` は「起きないことの確認」）を、記録の状態機械のテスト（`devices_test.go`）で、全マス総当たりで確かめる。台帳の読み込みは、壊れた記録、状態と B・K の矛盾、途中の電源断（一時ファイルだけが残る）を確かめる。
- B の表は、60 マス（`pairingMachine.test`）。保存の失敗と読み戻しの不一致、窓の ID が古い通知、二重押下、重複した GRANT を含む。
- 結合テスト: 本物のブリッジと端末のコードで、発行 → B で接続 → コードの入力 → K を受け取る → B の拒否 → K での質問、失効後の拒否、再発行後の旧 K の拒否。
